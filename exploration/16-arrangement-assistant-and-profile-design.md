# 安排助手：真实场景转化、数据边界与用户画像设计

**状态：探索阶段设计基线（2026-09-26）**  
**北极星：** 让人用一句话把意图变成一份可看、可改、可确认的日轨道草案；助手不替人假设空闲、优先级或人生规律。

## 1. 先纠正现有问题

旧界面将任何文本依次投到 09:00、13:00、19:00。这不是“预览”，而是虚构安排：它看似降低操作成本，实际把最关键的不确定性藏起来，用户只能先相信再纠正。

本轮的规则是：

1. 说清具体时间，才在日轨道显示具体锚点。
2. 只说“下午/晚上”，显示为时间窗，不假装知道开始时刻。
3. 没说时长或时间，只生成可复用事件对象，并明确问一个最小问题。
4. 检测冲突、找空档、写入任务或计划，均发生在用户看过实际轨道预览并确认之后。
5. “完成”默认记录点击完成时刻；复盘时再补充实际投入或结果，永不强迫填写。

## 2. 真实场景转化基准

| 场景输入 | 必须提取 | 不可擅自补全 | 预览应该是什么 | 下一步 |
| --- | --- | --- | --- | --- |
| “今天下午 3 点到 4 点半复习数据结构，晚上 8 点跑步 40 分钟” | 两件事、15:00/90 分钟、20:00/40 分钟 | 轨道类型可建议但不可写死 | 两张真实高度的轨道卡片 | 校验已有课程/锁定事件；确认写入 |
| “下午处理毕业设计” | 一件事、下午软时间窗 | 时长、精确起点 | `下午可安排 · 时长待定`，不落格 | 只问“预计多久？” |
| “整理英语错题，明早有课” | 一件待办、一条课程约束 | 给待办安排到早上 | 事件对象在待安排区；课程占用作为约束 | 问“希望今天还是哪天安排？” |
| “会议拖到 17:30，帮我重排今天” | 受影响的时间块与重排意图 | 移动锁定块、删除事项、跨天挪动 | 仅显示受影响区域的 before/after 双层草案 | 用户选择接受/逐项保留 |
| “今天没做完，把剩下的明天再安排” | 未完成任务与重排意图 | 认为任务已完成或估计进度 | 未完成量 + 明日可用空档的草案 | 确认后生成新版本，不覆盖旧计划 |

### 转化验收指标

- **提取覆盖率：** 文本中的任务、明确时间、时长、日期、限制被逐项抽取；测试集按字段而不是“看起来像对”评分。
- **不虚构率：** 没出现于文本/显式偏好/已确认日历的时间，不得成为确定安排。
- **澄清负担：** 只问阻止可执行预览的最少一个问题；可不问的字段留到复盘或编辑。
- **可接受率：** 草案被确认、局部编辑、完全放弃的比例；“编辑原因”优先于简单成功率。
- **约束正确率：** 与课程、锁定块、用户已经确认的安排零冲突；多轨可并行但同轨不可重叠。

## 3. 助手的产品流

```
说/输入 → 本地结构化提取 → 不确定项最小澄清
      → 约束引擎生成“未写入”日轨道草案 → 实际轨道预览
      → 用户逐项确认 / 编辑 / 拒绝 → 事务化写入
      → 开始/完成等真实事件 → 晚间复盘（可选） → 可撤销的画像信号
```

### 助手界面

- 顶部不是功能按钮墙，而是近期一轮对话与当前草案状态。
- 输入框上方保留三个轻量意图气泡：`安排今天`、`重排`、`导入课表`。点击只把可编辑的起始句插入输入框。
- 文本/语音统一先落为可编辑文本；语音识别失败时不阻断键盘输入。
- 草案卡片用真实相对位置画日轨道缩略图；未定事项留在“待决定”而非伪装成时间块。
- 草案提供逐项删除、改时长、改时间窗、选轨道；底部只有一个清晰的“确认写入 n 项”。
- 对需要联网理解的请求，先显示最小数据包、目的和“发送/继续离线”选项；发送后仍只获得草案。

## 4. 后端：应获取什么，绝不获取什么

### 本地数据（默认，帮助核心功能）

| 数据 | 用途 | 保留 / 控制 |
| --- | --- | --- |
| 任务对象、标签、用户填写的截止时间/时长 | 事件复用与排序 | 用户可改删；本地数据库 |
| 课程与日程约束、锁定状态、轨道 | 冲突检查与空档生成 | 不上传；可按来源删除 |
| 用户明确确认的计划版本、逐项编辑/拒绝 | 对比草案和真实选择 | 只保留最小结构化操作，不记录输入原文 |
| 开始、完成、延期与可选复盘 | 今日回顾、事实性统计 | 完成无需填写；可修正、导出、清除 |
| 明确偏好（勿扰时段、模式、允许并行） | 生成草案 | 单独设置、随时关闭 |

### 不应收集/推断

- 不采集通讯录、后台位置、通知内容、其它 App 使用记录或设备标识来“猜”行为。
- 不把聊天全文、课表全文、所有历史任务或原始复盘一股脑发送给模型。
- 不推断人格、心理/身体健康、学习能力、经济状况、社交关系或“自律程度”。
- 不将 API key 放进 APK；不可把调试日志当审计库。

Android 官方建议最小化权限和收集，并对敏感访问提供透明披露；对 LLM 还应在发送前净化和最小化上下文、最小权限并过滤输出。[Android 权限最小化](https://developer.android.com/privacy-and-security/minimize-permission-requests) [Android AI 敏感信息防护](https://developer.android.com/privacy-and-security/risks/ai-risks/sensitive-information-disclosure)

### 未来在线服务契约

`Android App → 本地 Context Builder → 用户预览 → HTTPS Backend → 模型 Provider`

1. **Context Builder** 依据工具做 allowlist，不读取全库。例：`重排`仅发送受影响任务的匿名引用、时长/截止日期、30 天内必要硬约束、用户选择共享的偏好聚合；任务 ID 替换成请求内短引用。
2. **Backend** 持有 provider key，做认证、速率限制、PII/秘密脱敏、schema 验证、内容审计和超时/重试；不保留原始提示词或模型响应，仅保留不含内容的结果码、耗时、契约版本。
3. **Tool boundary**：模型只能提出 `create_task_draft`、`propose_segments`、`summarize_confirmed_feedback` 等 typed proposal，不能直接写 Room、发通知、改已锁定块。
4. **App validator** 再次校验版本、请求 ID、时间颗粒度、冲突、锁定块、手动顺序和作用域；失败则回退到本地确定性草案。

工程已有 `AiAdvisorRequest`、确认前预览、返回结构校验和本地回退。下一阶段应新增 `IntakeAndSchedule` 的版本化 typed contract，而不是让聊天框直接连接 provider。

## 5. “用户画像”应改称为可控的安排信号

“画像”不是对人的判断，而是可被查看、修正、撤回的安排证据。NIST 的隐私框架把控制、沟通与保护和识别/治理并列；因此每个信号必须说明来源、用途、置信度和删除入口。[NIST Privacy Framework](https://www.nist.gov/privacy-framework/getting-started-0)

### 三层模型

1. **显式层（立即生效）**：用户选择的参与模式、偏好时间窗、勿扰时段、能否并行、提醒开关、课程与锁定事项。它不是推断。
2. **事实层（不可伪造）**：用户确认的计划、开始/完成/延期、实际用时/进度（如果用户填写）、对草案的接受/修改/拒绝。每条都带来源 ID 和可纠正关系。
3. **建议层（可撤销）**：只从足量事实统计出低风险聚合，例如某类别实际用时中位数、常被接受的时间窗、草案编辑率。显示样本数、观察窗口、置信度；未达到阈值不输出建议。

### 首批可上线信号

| 信号 | 最低样本与窗口 | 呈现 / 使用 | 失效与控制 |
| --- | --- | --- | --- |
| 类别实际时长中位数 + 离散范围 | 同类别 5 次已确认反馈，近 60 天 | “课程任务通常记录为 45–60 分钟”作为可选默认值 | 90 天未更新降权；一键关闭/删除来源 |
| 时间窗接受分布 | 同一类别 8 次用户确认安排，近 8 周 | 在空档中排序，而非强制排入 | 用户改一次即可覆盖单次偏好 |
| 草案修订模式 | 10 份已完成草案 | 决定先展示多大程度的细节 | 只调整界面密度，不判断能力 |
| 复盘节奏 | 4 次主动进入复盘 | 温和建议回顾入口，不发强制提醒 | 关闭即停止 |

任何“预测完成率”“效率分数”“学习能力标签”均不做。个人信息系统的价值来自采集、整合、反思和行动的闭环，而不是把统计结论伪装成人格判断。[Lived Informatics Model](https://pmc.ncbi.nlm.nih.gov/articles/PMC12435389/)

### 数据模型建议

```kotlin
data class ProfileSignal(
    val key: ProfileSignalKey,       // CATEGORY_DURATION / PREFERRED_WINDOW / DRAFT_EDITING
    val value: ProfileSignalValue,   // 结构化值，非模型自然语言结论
    val sampleCount: Int,
    val windowStart: LocalDate,
    val windowEnd: LocalDate,
    val confidence: SignalConfidence,
    val sourceIds: List<String>,
    val status: SignalStatus,         // PROPOSED / CONFIRMED / DISMISSED / EXPIRED
    val expiresAt: Instant,
)
```

保留现有 `ProfileEvidence` 作为来源可追溯的事实摘要；新增 `ProfileSignal` 不覆盖事实、不能把自身再当训练来源。Room 表按 `sourceFingerprint` 幂等，清除源事实后级联失效信号；导出/删除必须覆盖信号、会话草案和匿名审计。

## 6. 本轮实现与下一步

本轮已把本地文本转化器改为结构化、可单测的规则：明确时间才落时间点，软时间窗保留为软约束，缺时长/时间只产生澄清项。三个真实场景已转为自动化测试。

下一迭代按依赖顺序实施：

1. 为日轨道提供 `ArrangementContextSnapshot`（可用空档、锁定块、轨道、时区、当天日期）。
2. 让本地约束引擎生成 `PlanProposal`，并以可视轨道草案替代当前助手的静态缩略图。
3. 新增 `agent_proposals`、`proposal_items`、`proposal_decisions` 的可删除本地表，记录“接受/编辑/拒绝”的结构化决定，不存聊天全文。
4. 以 `ProfileSignal` 取代自由文本画像结论；设置页展示来源、样本、作用、关闭和删除。
5. 后端 ready 后再接入 `IntakeAndSchedule/v2`；不在 Android 客户端或数据库写入密钥。

## 7. 对抗性审查

- **模型误解一句话怎么办？** 输出只是一份可编辑草案；时间不明不落格，任何写入需要确认。
- **模型建议与课程冲突怎么办？** 本地硬约束校验拥有最终否决权，模型无写库权限。
- **“画像”变成监控怎么办？** 只使用用户确认的最小结构化事件；来源可见、可改、可删、可过期；不采集跨 App 行为。
- **数据不足却假装个性化怎么办？** 样本阈值与置信度显示；不足时使用中性默认值并说明。
- **网络/模型不可用怎么办？** 本地解析、约束和确定性草案仍可工作；不把失败转成静默自动安排。
- **用户因编辑成本放弃助手怎么办？** 先由语音/文本降低输入成本，再只问一个阻塞问题；常见操作保持轻量，复杂调整放入轨道直接操作。
