# Repland 组件级 UI 对标与落地规格

> 版本：v1.0
> 日期：2026-09-25
> 目的：补充 [`09-ui-redesign-competitor-research.md`](09-ui-redesign-competitor-research.md) 中不足的组件级细节，明确卡片、任务行、时间块、底部抽屉、创建流程、详情页和动效如何实现。
> 状态：设计基线，尚未进入代码实现。

## 0. 先纠正上一轮的不足

上一轮已经判断“不能把所有能力铺在首屏”，但还停留在页面结构层，没有回答以下实际问题：

- 哪些内容应该是卡片，哪些内容应该是列表行？
- 卡片内到底放几个信息层级？
- 任务状态、时间、优先级和主操作如何不互相抢夺？
- 当前任务、下一任务、待安排任务、草案任务是否使用同一种容器？
- 添加任务的每一步如何落在屏幕上，并且如何返回？
- 详情页是全屏、抽屉还是弹窗？不同屏幕宽度如何变？
- “看全局”的任务总览如何避免重新成为一个大仪表盘？

本报告不再只说“简洁、克制、Apple 风格”，而是把所有高频组件拆成可实现的视觉和状态规格。

## 1. 竞品组件层取经

### 1.1 Apple：复杂数据用列表承载，卡片只用于独立主题

Apple HIG 对列表的建议非常直接：列表适合表达可扫描的文字、分组和层级；条目内容应简短，过多内容应该进入详情，而不是继续把行撑大。列表还可以支持选择、添加、删除和重排；详情关系使用 disclosure indicator，而不是把详情内容直接塞进列表。

这意味着 Repland 的普通任务必须是“列表行”，而不是每一项都是独立卡片。卡片应只用来表达具有完整边界的单一主题，例如当前执行区、负载摘要、草案变更摘要。

参考：[Apple Lists and Tables](https://developer.apple.com/design/human-interface-guidelines/lists-and-tables?changes=_5)、[Apple Layout](https://developer.apple.com/design/human-interface-guidelines/layout)、[Apple Design Principles](https://developer.apple.com/design/human-interface-guidelines/design-principles)。

### 1.2 Material 3：卡片有三种语义，不是所有容器都要有阴影

Material 3 将卡片分为 Elevated、Filled 和 Outlined 三类。它们的区别不是“哪个更好看”，而是与背景分离的强度不同：Filled 提供轻微区分，Elevated 提供层次，Outlined 用边界强调独立性。Android 文档也明确把卡片定义为承载单一主题内容和动作的容器。

对 Repland 的决定：

- 普通任务行：不用 Card，使用列表 + 分隔线/分组背景。
- Now 卡：Filled card，表示当前唯一主上下文。
- 负载摘要：Filled card 或无边界 section，不使用阴影。
- 草案变更：Outlined card，表示“尚未生效的提案”。
- 冲突/不可行：Outlined + 语义色，不使用整块红色背景。
- 拖拽中任务：临时 Elevation，不是默认状态。

参考：[Material Cards](https://github.com/material-components/material-components-android/blob/master/docs/components/Card.md)、[Android Compose Card](https://developer.android.com/develop/ui/compose/quick-guides/content/create-card-as-container?authuser=2)。

### 1.3 Material ListItem：任务行要有一条、两条、三条的层级，而不是任意堆内容

Material 的 ListItem 区分 one-line、two-line 和 three-line。Repland 的任务列表默认使用 two-line：第一行是任务标题，第二行是“时间/状态摘要”。只有在待确认或冲突状态下，才暂时使用 three-line；描述不进入普通列表行。

参考：[Material 3 ListItem API](https://developer.android.google.cn/reference/kotlin/androidx/compose/material3/ListItem.composable)。

### 1.4 Bottom sheet：适合局部决策，不适合塞一整个长表单

Material bottom sheet 适合承载补充内容，能够通过下滑、关闭按钮或系统返回退出；它不会破坏用户当前上下文。Repland 用 bottom sheet 做“选择时长、安排日期、处理反馈、更多属性”，不用它装完整任务对象的全部字段。

参考：[Material Bottom Sheets](https://m1.material.io/components/bottom-sheets.html)、[Material 3 Compose release](https://developer.android.com/jetpack/androidx/releases/compose-material3)。

### 1.5 竞品的具体容器分工

| 产品/系统 | 普通内容容器 | 重点容器 | 可借鉴点 | Repland 取舍 |
| --- | --- | --- | --- | --- |
| Structured | 时间线任务块、Inbox 行 | 今日时间线 | 时间先于字段；未安排任务另存 Inbox | 取时间线与 Inbox，不复制满屏彩色任务块 |
| Todoist | 紧凑任务行 | Quick Add、Today/Upcoming | 输入优先，元数据后置 | 取快速捕获，不提前引入复杂标签过滤 |
| TickTick | 列表行、多视图条目 | 日历/时间线 | 同一任务在多个视图保持一致 | 取视图投影，不把多个视图叠在一屏 |
| Sunsama | 每日任务条目 | 负载与时间盒 | 计划时长和实际时长分开 | 取负载反馈，不强制每日仪式 |
| Routine | 任务列表 + 日历块 | Agenda/Console | 安排日期、占用时段、推迟分开 | 取三种关系，不照搬桌面 Console |
| Apple | 分组列表、详情页、Sheet | 选中行/详情卡 | 列表用于扫描，详情用于深入 | 取列表-详情关系，不模仿 iOS 皮肤 |
| Material 3 | ListItem、Card、Sheet | 状态卡和拖拽状态 | 容器有语义，动作有反馈 | 取 Android 原生触控和返回行为 |

## 2. 容器决策树：何时用卡片，何时用行

### 2.1 使用列表行的条件

满足以下任意两项，就必须优先使用列表行：

- 用户要连续扫描 4 项以上。
- 每项信息结构相同。
- 用户会频繁完成、排序、筛选或打开下一层。
- 内容主要是文本和少量状态。
- 用户需要比较多个项目。

任务列表、Inbox、历史记录、画像证据均属于列表行。

### 2.2 使用卡片的条件

卡片只承载一个“决策主题”，并且必须有清晰的内在边界：

- 当前正在执行的任务。
- 今天负载与可用时间的对比。
- 计划草案的变更摘要。
- 一次语音解析后的结构化预览。
- 一个需要用户处理的冲突。

卡片不能只因为“看起来比较现代”而存在。若删除边框后内容仍然自然地属于同一列表，就不应该是卡片。

### 2.3 使用底部抽屉的条件

- 当前页面上下文仍然有价值。
- 决策不超过 5 个选项。
- 内容是局部编辑，不需要看完整历史。
- 用户需要快速选择后回到原处。

日期选择、时长选择、延期原因、更多属性适合抽屉；任务详情、执行历史、复杂草案比较不适合强行塞进抽屉，应使用全屏详情。

## 3. 设计令牌和空间节奏

### 3.1 基础空间

使用 4dp 基础单位，主要节奏只允许：`4 / 8 / 12 / 16 / 20 / 24 / 32`。避免当前界面中出现多个随意的 18dp、20dp、28dp 圆角和随机间距。

| 层级 | 水平内边距 | 上下间距 | 适用 |
| --- | ---: | ---: | --- |
| 页面 | 20dp 手机；24–32dp 平板 | 16dp | 页面内容 |
| Section | 0–4dp | 24dp | 今日、任务分组 |
| ListItem | 16dp | 12–16dp | 普通任务行 |
| 主卡 | 20dp | 20dp | Now、草案摘要 |
| Bottom sheet | 24dp | 16dp | 局部选择 |
| Dialog | 尽量不使用 | - | 仅确认破坏性操作 |

### 3.2 圆角和阴影

| 元素 | 圆角 | 默认阴影 |
| --- | ---: | ---: |
| 普通任务行 | 0 或 12dp 容器 | 0dp |
| Now 卡 | 20dp | 0–1dp |
| 草案卡 | 16dp | 0dp，使用边框 |
| Bottom sheet | 顶部 28dp | 系统 scrim/层级 |
| FAB/主按钮 | 16dp 或全圆 | 1–3dp |
| 拖拽中 | 保持原圆角 | 临时 4–8dp |

当前“每个组件都是 20dp 大圆角卡片”必须终止。圆角是分组语义，不是品牌装饰。

### 3.3 颜色层级

- 页面底色：低对比、稳定、不与任务颜色竞争。
- 主文字：深墨色，至少 4.5:1 对比度。
- 次文字：只用于日期、来源、说明；不能承载关键状态。
- 主行动色：只出现于当前主按钮、选中状态、Now 卡强调。
- 类别色：最多作为 3–4dp 左侧色条或小图标，不给整个卡片染色。
- 风险色：橙色/红色配合文字，例如“超出可用时间 35 分钟”，不能只显示红色。

## 4. 组件一：任务行 TaskRow

### 4.1 默认结构

```text
┌────────────────────────────────────────────┐
│  ○  复习高数第三章                         › │  16dp
│     今天 20:00 · 60 分钟                    │  14dp
└────────────────────────────────────────────┘
```

具体结构：

- 左侧：48dp 点击区内的完成/状态控件，视觉图标 20–24dp。
- 中间：标题最多两行；默认 16sp / Medium。
- 第二行：只显示一个组合摘要，例如“今天 20:00 · 60 分钟”“待安排”“已超时 12 分钟”。
- 右侧：默认不放大按钮；使用 24dp chevron 或更多菜单。
- 整行点击打开详情；完成控件独立点击完成，不能触发详情导航。
- 行与行之间使用 1dp 分隔线或 8dp 分组间距，不同时使用厚边框、阴影和大背景。

### 4.2 状态变体

| 状态 | 视觉变化 | 主动作 |
| --- | --- | --- |
| 待安排 | 第二行显示“待安排”，不显示虚假时间 | 打开详情/安排 |
| 已安排 | 第二行显示日期与时长 | 打开详情 |
| 进行中 | 左侧控件变为暂停/计时语义，行底部可有 2dp 进度线 | 继续/完成 |
| 待确认 | 使用浅琥珀色小标签“待确认”，整行保持中性 | 完成/部分完成/延期 |
| 逾期 | 时间摘要前加“逾期”，图标+文字，不只靠红色 | 改期/继续 |
| 已完成 | 标题降低对比度、文字划线可选，不隐藏到删除 | 查看记录 |
| 冲突 | 增加“冲突”标签和细边框 | 查看冲突 |

### 4.3 为什么不做“大任务卡”

大卡适合展示一个主题，但用户任务列表需要比较多个项目。当前每张卡都包含描述、状态按钮、空白和圆角，造成三个问题：

1. 一屏看不到足够任务，用户无法形成全局判断。
2. 每个任务看起来都同等重要，真正的当前项无法突出。
3. 卡片内按钮使完成、打开、开始之间的点击意图变模糊。

### 4.4 Compose 落地建议

使用 `ListItem` 或自定义 `TaskRow`，为每项提供稳定 key；不要使用可变列表直接驱动 UI。使用 `Modifier.minimumInteractiveComponentSize()` 或显式 48dp 点击区；标题和摘要都提供语义描述。

## 5. 组件二：Now 卡

### 5.1 它是唯一允许“大卡片感”的工作组件

Now 卡不是任务详情，也不是时间线，它只承载“此刻的一个行动”。

```text
现在
复习高数第三章
今天 20:00–21:00 · 还有 25 分钟开始

[开始]                                  ⋯
```

进行中：

```text
正在进行 · 18 分钟
复习高数第三章
预计还剩 42 分钟

[标记完成]        [记录部分完成]
```

超时：

```text
已超出预计 12 分钟
复习高数第三章
你可以继续、完成或调整剩余内容

[继续] [处理]
```

### 5.2 Now 卡的字段边界

必有：标题、当前状态、相对时间、一个主动作。

可选：预计时长、剩余时间、任务类别小图标。

不放：完整描述、优先级选择器、所有执行日志、AI 长解释、画像分数。

### 5.3 视觉参数

- Filled surface，主色只占卡片背景的轻微色阶。
- 标题 20sp，状态 12–14sp，时间 14sp。
- 主按钮为 FilledTonal 或 Filled Button，根据状态语义切换。
- 右上角更多菜单只包含编辑、安排、暂停计时等次要操作。
- 卡片出现/消失时保持位置连续；任务变化不让下面整页跳动。

## 6. 组件三：负载摘要 CapacitySummary

不是“进度条装饰”，而是计划决策的数据摘要。

```text
今天的安排
3 小时 20 分 / 可用 4 小时
还剩 40 分钟空间                       查看计划 ›
```

状态变体：

- 可行：`3h20 / 4h`，中性色。
- 接近上限：`3h50 / 4h`，加“余量较少”。
- 超量：`4h35 / 4h`，橙色文字“超出 35 分钟”，提供“调整安排”。
- 缺少时长：`还有 3 项未估时`，提供“补充估时”而不是计算假进度。

不要画三根“课程/专注/休息”示意条。只有真实数据足够时，才画一个比例条；默认用文字和一个轻量横线表达即可。

## 7. 组件四：任务总览台

### 7.1 顶部工具栏

```text
任务                              搜索   ＋
[收件箱] [今天] [待安排] [逾期] [已完成]
```

- 标题 22sp，不写冗长副标题。
- 搜索进入独立搜索状态，不能在页面顶部常驻一个大搜索框。
- 快捷视图是横向滚动 FilterChip，当前只突出一项。
- 加号进入任务捕获，默认保存到收件箱。

### 7.2 分组头

```text
需要处理                         2
```

分组头只有标题和数量，右侧可折叠。分组间距 24dp，行间距 0/分隔线。已完成默认折叠，并显示数量，不要把完成任务挤在活跃任务下方。

### 7.3 批量与滑动动作

- 默认不展示批量选择栏，长按进入选择模式。
- 选择模式顶部出现“完成 / 安排 / 延期 / 删除”，并提供取消。
- 左右滑动不是唯一操作；所有滑动动作都有菜单替代。
- 删除使用可撤销 Snackbar，破坏性清除本地数据才使用确认 Dialog。

### 7.4 总览台不展示的东西

- 每项任务的完整描述。
- AI 解释全文。
- 所有画像证据。
- 每项任务的完整按钮组。
- 没有真实数据的图表。

## 8. 组件五：时间块 ScheduleBlock

### 8.1 时间轴中的任务块

```text
14:30 ─┐
       │  复习高数第三章
       │  60 分钟
15:30 ─┘
```

视觉规则：

- 左侧时间刻度统一，不让每个任务自己决定时间格式。
- 块内第一行标题，第二行时长/类别；描述永不进入时间块。
- 任务块背景只使用低饱和语义色，课程/休息/锁定时间使用不同图标与边界线。
- 高度与真实时长成比例，但设置最小高度 48dp，避免短任务不可点。
- 并行轨道只在有重叠事件时出现；没有并行事件不展示空轨道。

### 8.2 空档操作

点击空档打开小型创建 sheet，自动带入日期和开始时间；顶部显示“安排到今天 14:30”，用户仍可改时间或切换为只安排到当天。

### 8.3 拖拽操作

- 拖拽时任务块抬升、落点显示吸附位置。
- 松手后显示 Snackbar：`已移到 15:00–16:00 · 撤销`。
- 如果进入课程/锁定区域，显示冲突摘要和“仍要并行安排”选项，不静默覆盖。
- 所有拖拽操作有“编辑时间”按钮替代，满足无障碍和单手场景。

## 9. 组件六：渐进式创建界面

### 9.1 第一阶段：捕获底部栏

不是 AlertDialog，而是从底部出现的轻量 sheet，默认高度约 220–280dp：

```text
────────────────────────────
接下来要做什么？
写下任务……                 🎙

先保存到待安排       安排到今天
────────────────────────────
```

- 输入框自动获得焦点。
- 键盘上方保留麦克风和提交动作。
- 点击外部区域不丢草稿。
- 关闭时提示“已保留草稿”或直接自动保存到收件箱，避免数据丢失。

### 9.2 第二阶段：意图选择

用户输入后，只问一个问题：

```text
你想怎么处理？

[现在开始]  [安排今天]  [先放着]
```

三个选项使用等宽、同层级按钮，不用颜色暗示唯一正确答案。

### 9.3 第三阶段：按选择推进

选择“安排今天”后才显示：

```text
安排到今天

[只安排到今天]
[安排具体时段]
[只设置截止时间]
```

选择“具体时段”后才出现时间和时长；选择“只安排到今天”直接完成，不再追问。

### 9.4 语音解析预览卡

```text
原始输入
今晚八点复习高数，大概一小时

识别建议
今天 20:00 · 约 60 分钟

[采用建议] [逐项修改] [仅保存原文]
```

这是一张 Outlined card，不是成功结果卡。解析失败的状态：

```text
我保留了你的原话，还没有识别出可靠时间。
[先保存] [手动安排]
```

## 10. 组件七：任务详情页

### 10.1 顶部区域

```text
< 返回                                  …

复习高数第三章
待开始 · 今天 20:00 · 60 分钟

[开始]
```

顶部固定主动作，向下滚动后仍保留一个紧凑的状态栏或底部 CTA；不能让用户滚回顶部才能开始任务。

### 10.2 Section 结构

1. 下一步：当前任务最小可执行动作。
2. 时间：计划时段、截止时间、实际耗时分开显示。
3. 任务说明：无内容则不显示空占位。
4. 更多属性：类别、优先级、估时、来源、并行轨道。
5. 执行记录：默认最近一次，可展开历史。
6. 画像依据：只在有足够样本时显示。
7. 建议：只在有上下文的 Agent/Workflow 结果时出现。

每个 section 使用轻量标题 + 内容，不要每个 section 再嵌套一张圆角卡片。

### 10.3 执行反馈 sheet

完成后第一层只问状态：

```text
这次进展如何？

[完成] [完成一部分] [延期]
```

选择“完成一部分”后出现：

```text
完成了什么？
[输入]
剩余内容会保留在任务中。
[保存反馈]
```

选择“延期”后出现四个真实决策：继续、拆分、改期、放弃；而不是只打开日期选择器。

## 11. 组件八：草案变更卡

草案不能像普通任务一样混在当前计划里。使用 Outlined card：

```text
计划建议                         未确认
由于新增“实验报告”，今天将：

移动  复习高数       20:00 → 21:00
延后  整理笔记       今天 → 明天
超量  预计多出 35 分钟

[确认建议] [编辑] [保留当前计划]
```

用户要先看到变化摘要，再决定是否看完整时间轴。Agent 的解释也应绑定这张卡，不在页面上单独出现一个聊天窗口。

## 12. 组件九：空状态、加载、错误和权限

### 12.1 空状态

```text
今天还没有安排
先记下一件事，之后再决定什么时候做。
[添加任务]
```

不要显示解释型长卡片、示意条或“给每一种节奏留位置”的品牌文案。

### 12.2 待安排状态

```text
还没有时间安排
任务已经保存，之后可以放到今天或某个时段。
[安排] [先保留]
```

### 12.3 解析失败

保留用户原文，并提供本地手动路径；不能出现全屏错误或空白。

### 12.4 通知/语音权限

权限请求必须在用户触发相关能力时出现，并说明用途；权限被拒绝不影响任务创建、列表和手动计划。

## 14. 动效逐组件规格

### 14.1 任务完成

- 触控反馈：80–120ms ripple。
- 状态图标：120–180ms 从圆环到勾选。
- 标题：150ms 颜色降低；是否划线由可访问性和偏好决定。
- 行位置：不立刻移除，短暂保留并给出撤销；用户确认后才移动到已完成分组。

### 14.2 创建步骤

- 当前步骤内容向左淡出 120–160ms。
- 下一步骤从右侧 8dp 进入 160–200ms。
- 键盘保持连续，不让整张 sheet 重新跳动。
- 后退时反向回到上一步，不清空已输入内容。

### 14.3 详情展开

- 只展开用户点击的 section。
- 使用 `AnimatedVisibility` 或 `animateContentSize` 时保持稳定 key；不能因为日志追加让整个页面回到顶部。
- reduced motion 下直接展开，不做高度动画。

### 14.4 时间块拖动

- 拖动跟手，落点吸附 5/10/15 分钟刻度由用户设置决定。
- 松手后用短暂高亮表达结果；不弹大 Dialog 打断。
- 进入冲突区使用边框变化，不持续闪烁。

## 16. 对抗性复核

### 反例 1：任务只有两项，列表行是不是太朴素？

不是。少量任务时使用 Now 卡 + 下一项；列表行只负责补充任务。卡片和列表各自承担不同语义，不用用大卡片把空白撑满。

### 反例 2：比赛展示需要更多视觉亮点

视觉亮点来自真实状态变化：语音转结构化任务、时间块进入计划、任务开始计时、超时后反馈和画像反哺。用装饰条、渐变和多色卡片堆“亮点”会让关键能力变得不可信。

### 反例 3：如果用户想一次性编辑全部字段

详情页的“更多属性”允许一次性展开；重度模式还可以提供“快速完整创建”。渐进披露是默认路径，不是能力上限。

### 反例 4：卡片减少后会不会失去品牌辨识度

品牌不靠每一项都加圆角，而靠稳定的任务行、Now 卡、时间块、语义色和动效节奏。组件少而一致，辨识度更强。

### 反例 5：为什么不用全屏弹窗完成创建

完整编辑任务是一个长期对象，不应该被局部弹窗限制；快速捕获适合 sheet，完整任务详情适合页面，两个层级不能混为一谈。

## 17. 组件级验收标准

- [ ] 普通任务列表不再使用统一的大卡片。
- [ ] 每个列表行最多两行主内容，除待确认/冲突外不超过三行。
- [ ] Now 卡只有一个主要行动。
- [ ] 卡片容器均能说清楚“它承载的单一主题是什么”。
- [ ] 普通任务可在一屏看到至少 6 项或完整分组边界。
- [ ] 创建任务第一屏只有文本/语音输入和两个方向动作。
- [ ] 选择不同方向后，后续问题不同；不会每次弹出相同全量表单。
- [ ] 任务详情默认折叠描述、画像和历史。
- [ ] 计划草案使用明显的“未确认”边界，不能伪装成当前计划。
- [ ] 375dp 宽设备、横屏、平板、深色模式和加大字体下不破坏层级。
- [ ] 所有滑动/拖拽动作有可点击替代。
- [ ] 所有主按钮和状态控件触控区至少 48dp。
- [ ] reduced motion 下所有信息变化仍然可理解。
