# Agent / Workflow 候选与创新方向

> 状态：探索假设  
> 目的：在确定性核心稳定后，判断哪些能力适合 Agent 参与，并限定 Agent 的权限和输出形态。

## 1. 总体判断

Repland 不应从“用户问一句，Agent 替我操作整个应用”开始。更合适的架构是：

```text
确定性 Domain Core
  → 确定性 Workflow 组织输入、校验权限和保存结果
  → Agent 在受限上下文中生成建议/解释/草案
  → Workflow 校验 Agent 输出
  → 用户确认
  → Core 产生可回退的事实变化
```

Agent 的创新价值不是替代所有点击，而是处理传统应用中最难结构化的三类问题：

1. 把自然语言和不完整信息转成可编辑结构。
2. 在多个可接受方案之间解释取舍。
3. 从连续执行反馈中提炼下一次规划所需的模式。

## 2. 候选能力分级

| 候选 | Agent 角色 | Workflow 角色 | 权限建议 | 优先级 |
| --- | --- | --- | --- | --- |
| 任务理解 | 识别任务标题、目标、时长线索、依赖和缺失信息 | 收集原文、展示建议、确认后写入可编辑字段 | 不得覆盖已有用户字段 | 高 |
| 任务拆分 | 提供步骤和粒度建议 | 把建议变成待确认草案 | 只能创建草案，不直接写任务状态 | 高 |
| 动态排序解释 | 解释为什么排在前面、哪些因素影响排序 | 提供受影响任务和排序依据 | 不能修改初始优先级 | 高 |
| 冲突取舍 | 比较延期、拆分、轮换、降低目标等方案 | 限定冲突集合，记录一次性授权范围 | 只在当前冲突范围内生效 | 高 |
| 反馈后的重规划建议 | 根据真实反馈估计剩余工作、建议下一步 | 生成调整草案并等待确认 | 不能自动移动当前计划 | 高 |
| 每日总结 | 把结构化数据写成摘要，指出偏差和明日建议 | 汇总已确认反馈并控制数据范围 | 不能改变任务状态 | 中高 |
| 画像证据归纳 | 从反馈中提炼节奏、估时偏差和中断模式 | 保留来源、允许用户修改/删除 | 只能写入可审阅证据 | 中高 |
| 课表导入辅助 | 对模糊课程文本提出修正建议 | 展示解析预览并等待确认 | 不得无提示替换原始导入 | 中 |
| 自由聊天代办 | 解释和操作任意数据 | 很难限定范围和恢复语义 | 暂不开放 | 低 |
| 自动完成/自动延期 | 代替用户做现实结果判断 | 会破坏核心信任模型 | 禁止 | 禁止 |

## 3. 适合 Agent 化的核心体验

### 3.1 “我不知道怎么描述” → 结构化任务

用户可以先说：

> 下周要把数据库课程作业搞完，周三晚上有空，可能要先看完老师发的资料。

Agent 只输出：

- 可编辑任务标题。
- 可能的截止日期和不确定性。
- 预计工作量范围，而不是伪造精确时长。
- 依赖关系候选。
- 缺少的信息。

Workflow 再让用户确认哪些字段进入任务，最后仍由本地规划器决定是否能排入时间段。

### 3.2 “我现在该牺牲什么” → 冲突取舍

传统待办工具通常只告诉用户“冲突”或直接把任务挪走。Repland 可以把冲突变成一个决策面：

- 保证截止日期：压缩其他任务。
- 保证学习深度：拆成多天工作段。
- 保证今日休息：延后低优先级任务。
- 降低目标：先完成最低可交付版本。

Agent 的价值是解释每个方案的代价，Workflow 的价值是确保这些方案只影响冲突集合，用户的价值是确认选择。

### 3.3 “现实已经变了” → 反馈驱动的再规划

用户说“只完成了资料整理，代码还没开始”，系统不应直接把任务标记为完成。Agent 可以建议：

- 当前任务进度约为多少，等待用户确认。
- 剩余工作可以拆成哪些下一步。
- 依据用户可用时间生成多个后续方案。

最终结果必须落入既有的部分完成、追加反馈、调整草案和计划版本链路。

### 3.4 “我为什么总是做不完” → 可追溯的画像证据

Agent 可以从用户确认的记录中发现：

- 某类任务的实际耗时长期高于预计。
- 晚间工作段更容易被延期。
- 任务拆成 30–60 分钟段后完成率更好。

但结论要附带来源、置信度和时间范围，用户可以编辑或删除。不能生成没有证据的性格判断或“效率分数”。

## 4. Workflow 与 Agent 的边界契约

### Workflow 必须负责

- 确定输入范围和数据最小化。
- 检查当前用户是否有权触发该流程。
- 读取当前计划、硬约束、手动顺序和有效反馈。
- 限制 Agent 可见的任务范围。
- 校验 Agent 输出的结构、引用对象、时间重叠和约束冲突。
- 提供本地降级路径。
- 等待用户确认并以事务方式保存事实变化。
- 记录流程触发原因、用户选择和结果。

### Agent 可以负责

- 解析用户自然语言。
- 提出任务字段、拆分、排序和估时建议。
- 比较多个可行取舍并解释影响。
- 生成每日总结和下一步草案。
- 对反馈证据进行归纳。

### Agent 不应负责

- 直接写任务完成、延期、取消、替换状态。
- 直接替换当前计划。
- 删除任务、历史、日志或用户画像。
- 修改初始优先级、类别偏好、硬约束和用户锁定时间。
- 直接创建提醒或修改提醒设置。
- 读取与本次决策无关的完整个人数据。

## 5. 第一批创新应用建议

### A. 受约束的“决策型计划助手”

不是聊天机器人，而是嵌入计划草案中的“取舍解释器”：它读取 Workflow 已经筛选出的冲突集合，生成 2–3 个可比较方案，用户选择一个，系统生成可回退版本。

### B. 反馈型“现实校准器”

不是统计完成率，而是把计划时间、实际时间、进度和延期原因关联起来，告诉用户“下一次计划应该如何更接近现实”。输出仍然是建议，不是自动改规则。

### C. 低负担“任务理解器”

把自然语言、模糊时间和任务依赖转成最小字段建议，并在缺失信息时只提一个最重要的问题，避免传统应用要求用户一次性填写完整表单。

## 6. Agent 化的反例

以下方向暂时明确否决：

- 一个全局输入框，允许 Agent 读写所有任务和设置。
- Agent 看到时间变化后自动帮用户“合理安排”，不显示差异。
- 用模型判断用户是否完成了现实任务。
- 用模型自动改变优先级或类别偏好。
- 用模型把历史反馈浓缩成不可修改的个人标签。

这些方案看似减少操作，但会破坏 Repland 最重要的信任基础：用户知道发生了什么，并且可以拒绝、修正和回退。
