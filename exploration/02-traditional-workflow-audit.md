# 传统应用工作流盘点

> 状态：第一版盘点  
> 目的：找出传统应用中反复发生的跨页面、跨实体、规则密集型工作，并判断哪些适合先做成确定性 Workflow。

## 1. 术语先定下来

在本探索区暂时采用以下区分：

- **普通功能**：用户在一个页面完成的明确操作，例如新建任务、修改标题、调整一个时间段。
- **Workflow**：跨多个步骤、对象或页面，有明确起点、状态、结果和失败恢复方式的业务流程；默认由确定性规则驱动。
- **Agent**：在 Workflow 提供的受限上下文和权限范围内，输出理解、建议、解释或草案的能力；不是拥有全部数据写权限的万能助手。
- **决策**：用户确认后产生的可追溯结果，例如确认计划、确认延期、授权当前冲突由 AI 取舍。

这四个概念不能混用：Workflow 负责“流程一定怎么走”，Agent 负责“在允许的范围内给建议”，用户负责“哪些建议成为现实”。

## 2. 重复劳动与 Workflow 候选

| 传统重复工作 | 发生频率 | 主要痛点 | 是否适合 Workflow | Agent 适合参与什么 |
| --- | --- | --- | --- | --- |
| 新建任务后补全日期、时长、优先级、分类 | 高频 | 用户需要在多个字段和页面间反复判断 | 是，做渐进式任务收集流程 | 识别日期/时长/依赖并生成可编辑建议 |
| 任务或时间约束变化后判断计划是否失效 | 高频 | 每个入口都可能触发重算，容易漏提醒或漏更新 | 是，做统一计划失效与草案生成流程 | 解释影响范围和推荐取舍 |
| 新任务加入后处理容量和截止冲突 | 高频 | 用户需要手动比较多个任务、时间和截止日期 | 是，做冲突检测与决策流程 | 提供排序、拆分、延期、降低目标等方案 |
| 工作段结束后确认完成情况 | 高频 | 传统应用容易自动勾选或只提供一个完成按钮 | 是，做“待确认 → 反馈 → 后续动作”流程 | 根据反馈建议下一步，但不能替用户改状态 |
| 部分完成后计算剩余工作并重新安排 | 高频 | 剩余工作容易丢失，用户被迫重新创建任务 | 是，做剩余工作衍生与调整草案流程 | 建议拆分粒度和后续安排 |
| 延期后决定继续/拆分/改期/降低目标/放弃 | 中高频 | 单纯改日期会掩盖真正的计划问题 | 是，做延期决策流程 | 解释延期原因模式并比较方案 |
| 当前计划确认、提醒同步、历史版本保存 | 高频 | 多模块写入容易出现计划和提醒不一致 | 是，做确认提交事务流程 | 不应参与写入，只能解释提交结果 |
| 计划回退后恢复提醒和执行基准 | 低频但高风险 | 传统回退常常破坏后续记录 | 是，做可回退版本恢复流程 | 帮助用户比较版本差异，不直接恢复 |
| 每日回顾汇总完成、未完成、时长和进度 | 每日 | 手工整理成本高，容易只看完成数量 | 是，做每日回顾流程 | 生成摘要、发现偏差和提出明日建议 |
| 从反馈记录生成画像证据 | 中频 | 用户难以知道结论来自哪里 | 是，做证据聚合和修正流程 | 归纳模式，但必须展示来源并可编辑/删除 |
| PDF 课表导入、清洗、预览、确认 | 学期/周期性 | 解析、纠错、重复确认较繁琐 | 是，做导入预览流程 | 只在解析不确定时提示和建议修正 |
| 提醒计划重算 | 高频但隐蔽 | 提醒可能来自旧计划或草案 | 是，做确认计划到提醒的派生流程 | 不参与提醒权限和调度 |
| 数据导出和清除 | 低频高风险 | 需要明确确认和完整性保证 | 是，做一次性安全流程 | 不参与自动触发 |

## 3. 先做的五条确定性 Workflow

### W1：任务收集与补全

```text
用户输入
  → 保存最小任务
  → 检查可解析信息
  → 补充或确认日期/时长/类别/优先级
  → 标记待安排或进入计划草案
```

必须保证：即使解析失败，原始输入不丢失；用户可以跳过补全；Agent 不能覆盖用户已有标题或初始优先级。

### W2：计划失效与草案生成

```text
任务/时间/反馈/偏好变化
  → 记录触发原因
  → 计算受影响对象
  → 判断是否需要新草案
  → 运行本地规划器
  → 输出草案和风险
  → 等待用户确认
```

这条 Workflow 是当前最重要的架构抽象。它应替代多个 UI 入口各自拼装“重新生成计划”的做法。

### W3：冲突处理

```text
检测冲突
  → 锁定冲突集合
  → 展示容量、截止日期、硬约束和手动决定
  → 用户手动调整 / 选择方案 / 当前范围授权 AI
  → 生成可回退的新计划版本
```

冲突处理不能直接等价为“自动排序”。它首先是一个用户决策流程。

### W4：工作段反馈与后续动作

```text
工作段结束
  → 待确认
  → 完成 / 部分完成 / 延期 / 取消
  → 写入追加式反馈
  → 计算剩余工作和风险
  → 生成调整草案
```

Agent 可以在“后续动作建议”参与，但不能把工作段结束解释为任务已经完成。

### W5：计划确认提交

```text
草案编辑完成
  → 校验硬约束、重叠、任务范围和手动顺序
  → 生成计划版本
  → 更新当前计划
  → 从当前计划派生提醒
  → 返回确认摘要和撤销/回退入口
```

这条 Workflow 需要具备事务语义：计划版本、当前计划指针和提醒派生不能出现半成功状态。

## 4. 不要过早 Workflow 化的操作

- 修改一个任务标题、描述或类别：先保持直接编辑，不需要复杂流程。
- 调整一个时间块：直接操作即可，但要统一走冲突校验。
- 用户主动查看历史：查询，不应被包装成 Agent 对话。
- 导出 JSON：确定性调用，不能交给 Agent。
- 删除或清除数据：安全确认流程，不要用自然语言触发。

原则是：**Workflow 用来收敛跨步骤一致性，不用来给每个点击增加仪式感。**
