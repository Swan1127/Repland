# Repland UI 重设计与竞品取经报告

> 版本：v1.0
> 调研日期：2026-09-25
> 适用范围：Android 原生 Compose 端的今日、任务、计划、任务创建与任务详情
> 本轮结论：重做信息架构与交互节奏，保留现有领域模型、Room 数据和测试底座；本轮不直接改代码。

## 0. 结论先行

当前实现的功能方向没有错，问题在于把“能力说明”当成了“日常工作界面”。它更像一个功能演示页：标题很大、解释性卡片很大、任务全部平铺、字段一次性要求、每一项都像独立卡片。用户打开应用后需要先读懂产品，再找到自己真正要做的事。

这轮重设计必须倒过来：

> 首屏只回答“现在该做什么”；任务页只回答“我要管理哪一组任务”；创建只问“此刻最必要的下一个问题”；详情页再承载完整信息。

### 0.1 新方向

Repland 的默认体验改为 **Calm Control Center / 安静的任务控制台**：

- **Today / 今天**：面向执行，不是功能总览。首屏只显示当前或下一项、今日负载和一个待处理提示。
- **Tasks / 任务**：面向收集、筛选和处理。默认是紧凑分组列表，不是“大卡片瀑布”。
- **Plan / 计划**：面向安排和调整。时间轴、课程、固定事项、任务时段在这里统一查看与编辑。
- **Me / 我的**：面向偏好、模式、画像和数据。不要把复杂配置挤进今日页。

底部导航仍然维持四项，不增加“AI”或“统计”入口。AI 和 Workflow 依附在任务、计划和复盘的上下文里，不能成为另一个需要用户学习的平行产品。

### 0.2 本轮明确推倒的内容

以下内容不是小修小补，而是要在实现时移除或替换：

1. 今日页的“给每一种节奏留位置”解释型大卡片。它可以出现在首次进入引导或帮助页，不能常驻在工作面。
2. 任务页中所有任务都使用大圆角卡片、长描述和同等权重展示。
3. `TaskEditorDialog` 的一次性全量表单。
4. 把待确认、时间轴、其他活跃任务和所有任务属性同时塞入一个长滚动页。
5. 当前自绘的类图标。使用稳定的 Material Symbols/Material Icons 语义图标，保持一套线性图标风格。
6. 通过“教程式色块”和示意条表达尚未发生的真实安排。没有真实时间数据时不画像数据可视化的装饰条。

### 0.3 不推倒的底座

本轮 UI 重做不需要先重写数据库或重新发明领域模型：

- `Task`、任务状态、截止日期、预计/实际时长、执行日志继续作为事实来源。
- 多轨时间线、计划段、固定时间块、待确认工作段继续保留。
- Room 本地优先、事件与日志可追溯、AI 通过调试网关接入的方向继续保留。
- 现有测试要继续作为回归线；新 UI 应增加语义标签和状态覆盖测试。

## 1. 真实竞品研究：看它们如何降低复杂度

本轮只把官方产品页和官方帮助中心当作产品事实来源。视觉判断来自官方产品页公开的界面截图和操作说明；第三方截图不作为功能事实，只用于验证行业常见的信息密度。

### 1.1 Structured：把“今天”变成一条可执行时间线

Structured 的核心不是任务字段，而是打开应用后直接看到一天的时间线。它将任务分为有具体时间的时间线任务、全天任务、重复任务和没有日期/时间的 Inbox 任务；用户可以把 Inbox 中的任务拖到时间线。官方帮助也明确把“标题、日期、时长、时间”拆在创建路径中，而不是要求用户一次性写完整对象。

取经：

- Today 必须是一条真正可执行的主线，而不是产品说明书。
- “没有时间”是 Inbox/待安排状态，不是错误，也不应该被隐藏。
- 时间线可以承担安排，但不应该把所有详情都画在每一项上。
- 对 Android 的取舍：拖拽可以有，但要提供点击选择时间的等价路径，避免把关键能力押在手势上。

不照搬：Structured 的高饱和颜色和长时间线在任务多时会产生视觉噪声；Repland 使用更克制的状态色，只有当前项和风险项突出。

来源：[Structured 产品页](https://structured.app/)、[官方任务创建说明](https://help.structured.app/en/articles/338050)、[官方拖拽说明](https://help.structured.app/en/articles/338306)。

### 1.2 Todoist：快速捕获先于字段完整

Todoist 的 Quick Add 设计持续把“输入任务”放在第一位：最近的官方更新说明明确提到，Quick Add 打开时先让用户捕获内容，项目、日期等操作在输入后才出现；任务管理页也将语音输入、自然语言日期、Today 和 Upcoming 分成不同层次。

取经：

- 添加任务的第一步只有一个主输入框。
- 识别出的日期和时长应以可编辑的结构化建议出现，而不是暗中写入。
- Today 和 Upcoming 是不同问题：一个让人执行今天，一个让人看更远的安排。
- 任务列表的扫描速度优先于完整元数据展示。

不照搬：Todoist 的项目、标签、过滤器适合复杂用户，但 Repland 不把复杂过滤表达式提前放进 MVP；先把“待安排、今天、逾期、待确认”做成显式快捷视图。

来源：[Todoist 任务管理页](https://www.todoist.com/task-management)、[Todoist Quick Add 更新](https://www.todoist.com/cs/help/todoist/product-updates/2026-changelog-HD3jJAtLd)、[Todoist 日历布局](https://www.todoist.com/help/todoist/features/use-the-calendar-layout-in-todoist-lPHRQTu0o)。

### 1.3 TickTick：多视图是能力，不是默认堆叠

TickTick 把列表、日历、议程、时间线、看板、专注和统计都做成可选工作面。它的官方功能页强调：列表用于组织，日历用于安排，时间线用于查看时长和拖动调整。这个产品的成熟点不是“所有东西都在一屏”，而是同一个任务对象能够在不同视图之间保持一致。

取经：

- 任务对象和视图解耦；今天、任务、计划不应各自维护一份任务状态。
- 任务详情可以很丰富，但列表只显示做当前决定所需的信息。
- 视图切换应该是明确的模式变化，而不是一个页面继续无限增加区块。

不照搬：看板、矩阵、习惯和统计目前不是 Repland 的首要任务；如果把所有成熟能力提前放进导航，用户会误以为 Repland 是一个复杂的生产力套件。

来源：[TickTick 功能页](https://ticktick.com/features)、[TickTick 官方帮助中心](https://help.ticktick.com/)。

### 1.4 Sunsama：限制承诺量，减少“规划假象”

Sunsama 的每日规划不是单纯列出任务，而是把任务加入当天、填写预计时间、查看预计负载、调整顺序、可选时间盒，最后开始执行。它还区分 planned time 和 actual time。这一点对 Repland 很重要：计划不是装饰，必须让用户知道今天是否承诺过多。

取经：

- 负载提示应该是可行动的：“今天已安排 3 小时 20 分，可用 4 小时”，而不是一个脱离决策的完成率。
- 一天最多突出 1 个当前项和少量即将到来的项，其余任务进入列表。
- 复盘要服务于下次估时和安排，不变成统计成就页。

不照搬：Sunsama 的完整每日仪式适合重度计划用户；轻度用户不能被迫完成一套仪式。所以 Repland 把它设计成“可进入的计划检查”，而不是启动门槛。

来源：[Sunsama 每日规划](https://help.sunsama.com/docs/usage-guides/daily-planning/)、[Sunsama 时间盒](https://www.sunsama.com/features/timeboxing)、[planned 与 actual time](https://help.sunsama.com/docs/usage-guides/tasks/planned-and-actual-times/)。

### 1.5 Routine：把“安排到某天”和“占用某时段”分开

Routine 官方帮助明确区分三种动作：把任务安排到某一天、把任务放进具体时间块、把任务推迟到未来。这个区分非常值得引入 Repland，因为当前实现容易让用户把截止日期、计划日期和实际工作时间混为一谈。

取经：

- “今天要做”不等于“今天 14:00–15:00 做”。
- 详情页和时间轴应分别支持安排到日期与安排到时段。
- 延期是一个有意图的动作，不应退化成直接改日期。

来源：[Routine Planner](https://routine.co/features/planner)、[Routine Planning & Scheduling](https://help.routine.co/articles/6092827-planning-and-scheduling)。

### 1.6 Apple Reminders 与 Android 自适应设计：少而稳，层级自然

Apple Reminders 的官方说明把输入路径描述为“输入、听写或 Siri”，再通过列表、标签和智能列表组织内容；它没有要求用户在第一次记录时理解所有字段。Android 官方自适应设计则推荐 list-detail：小屏先显示列表，选中后进入详情；更大窗口可以并排显示列表和详情。

取经：

- 语音输入必须回到可编辑文本，不以语音结果直接替用户完成不可逆动作。
- 小屏使用“列表 → 详情”推进；平板/横屏可演化成列表 + 详情双栏。
- 视觉上让内容本身成为主角，减少装饰面板和解释文案。

来源：[Apple Reminders 官方入门](https://support.apple.com/guide/iphone/get-started-with-reminders-iphc7880ecd6/27/ios/27)、[Android list-detail](https://developer.android.com/develop/adaptive-apps/guides/list-detail)、[Android 自适应布局](https://developer.android.com/develop/ui/compose/build-adaptive-apps)。

## 2. 对当前版本的审查：问题是节奏，不是能力

### 2.1 今日页：首屏被解释性内容占据

现有模拟器截图中，第一眼依次看到“今日计划”“你的今天”“课程、休息和任务在同一时间轴”“给每一种节奏留位置”、三条示意条、语音入口、回顾入口、空状态和大号加号。对于第一次体验它能解释产品概念，但对于第二次以后每天使用，它把用户真正关心的“现在/下一项”推到了很后面。

改法：

- 去掉常驻解释卡；如果没有真实安排，空状态只显示一句“今天还没有安排”，加一个主动作“添加任务”。
- 有当前任务时，首屏只显示一张 Now 卡：任务名、剩余/开始时间、一个主按钮。
- 负载信息变成顶部一行小摘要，而不是一整块说明卡。
- 任务数量和说明文字降权，避免与当前行动竞争。
- 语音入口改为输入框右侧的麦克风，不能与“添加任务”“回顾”并排抢主操作。

### 2.2 任务页：每项任务都在“发表长篇自我介绍”

现有 `TaskCard` 使用大圆角容器、较大的内边距、描述文本和状态按钮。任务数量一多，纵向扫描成本迅速升高；任务标题、描述、状态按钮、类别等信息没有清晰的主次。

改法：

- 改为分组的紧凑任务行：左侧 24dp 状态控件，中间标题，下一行只放一个时间/状态摘要，右侧使用更多菜单或主动作。
- 描述不在列表默认展示；有描述时只用一个小标记提示“有说明”。
- 默认按“待确认 / 今天 / 待安排 / 逾期 / 已完成”分组，不把所有任务混在同一序列中。
- 分组可折叠，且记住用户最后一次状态；已完成默认折叠。
- 只有当前任务或需要确认的任务出现强调色和动作按钮，其余任务保持安静。

### 2.3 添加任务：当前对用户要求“先完成数据录入作业”

现有 `TaskEditorDialog` 同时展示标题、说明、分类、优先级、预计天数、预计时长和日期。它从数据模型出发，而不是从用户意图出发。尤其是“预计天数”和“总时长”同时出现，会让用户不清楚两者区别；日期还要求手动输入字符串，明显不像成熟移动端产品。

改法：

- 不再使用长表单 AlertDialog 承载创建任务。
- 改为底部捕获栏或全屏创建页：第一屏只有一句问题“接下来要做什么？”
- 保存任务和安排任务是两个不同阶段；用户可以先把想法保存进“待安排”。
- 只有在用户选择了“安排今天”或“设置截止”后，才询问日期/时长。
- 类别和优先级默认不打断输入，放在第二层“更多选项”；用户画像足够稳定后可以提供个性化默认值，但仍可修改。

## 3. 新信息架构：四个工作面

### 3.1 Today / 今天：只做当前决定

页面结构从上到下：

1. **紧凑顶部栏**：日期切换、今日负载小摘要、更多菜单。
2. **Now 卡**：
   - 未开始：`14:30 开始 · 还有 25 分钟`
   - 进行中：`已进行 18 分钟 · 预计还剩 22 分钟`
   - 超时：`已超出预计 12 分钟`
   - 未安排：不伪造时间，只显示“待安排”。
   - 主按钮只有一个：开始、继续、完成或处理反馈。
3. **下一项**：只展示一项；点击“查看今天”才展开时间线。
4. **需要我处理**：最多显示 1–3 个待确认/冲突/延期决策。
5. **今日安排**：可折叠的顺序列表或时间线摘要。
6. **待安排**：显示数量和最近一项，点击进入任务台。

首屏的内容预算：在小屏上不超过一张主卡、一个决策区和一个列表入口。没有安排时，首屏只保留添加入口和待安排入口，不显示假的节奏说明。

### 3.2 Tasks / 任务：任务总览台

用户提到的“整体任务观礼台”在产品中命名为 **任务总览台 / Task Control Center**。它不是把所有任务全部展示，而是提供任务的状态分流与批量管理。

顶部结构：

- 标题“任务”；右侧搜索和添加。
- 一行快捷视图：`收件箱`、`今天`、`待安排`、`逾期`、`已完成`。横向滚动，但默认只突出当前筛选。
- 可选排序：最近更新、截止时间、优先级；不把复杂过滤器常驻。

默认内容：

```text
需要处理       2
  □ 提交实验报告           今天 18:00       高
  ◷ 整理课堂笔记           待安排

今天           3h 20m / 可用 4h
  □ 复习线性代数           14:30–15:20
  □ 买生活用品             18:00 前

更晚           5
  …

已完成         12  ▸
```

任务行的视觉顺序是：完成控件 → 标题 → 时间/状态 → 极少量优先级标记。描述、分类、画像建议、执行日志都不在这里展开。

### 3.3 Plan / 计划：可编辑的时间关系

Plan 负责回答“这些任务怎么放进现实的一天”。

- 顶部是日期/周切换和视图切换：日、周；月视图后置。
- 日视图以时间刻度为主；任务块、课程、固定事项、休息以不同的形状/标签区分。
- 无具体时间的任务在底部 Inbox 带中；拖拽/点击后进入时段。
- 计划草案不是另一套页面，而是在计划页上方以“变更摘要”呈现：新增几项、移动几项、超出几分钟、受什么约束影响。
- 多轨并行只在真实有多条同时进行的事项时出现；没有并行数据时不展示空轨道。

Android 优势：

- 手机上通过底部抽屉编辑时间块，保持时间轴上下文。
- 横屏、平板、折叠屏使用 list-detail 或双栏：左侧任务/Inbox，右侧时间轴或详情。
- 系统返回支持从详情回到列表，从抽屉回到时间轴；不通过“关闭整个工作面”打断用户。

### 3.4 Me / 我的：把画像与设置放在正确的距离

分组列表而不是一张长配置页：

- 我的节奏：重度计划参与 / 中度干预 / 轻度执行。
- 提醒与系统：通知、语音、后台权限。
- 画像与记录：最近总结、估时偏差、数据来源、清除/导出。
- AI 与 Workflow：开关、权限范围、最近一次建议、失败回退。
- 数据：本地备份、导出、恢复。

模式不改变数据模型，只改变首屏的展示密度和默认操作：

| 模式 | 默认首屏 | 创建路径 | AI/Workflow 默认参与 |
| --- | --- | --- | --- |
| 重度计划参与 | 时间线、负载和计划差异更明显 | 可直接进入时长/时间/并行设置 | 提供多个方案和解释，用户逐项选择 |
| 中度计划干预 | Now + 下一项 + 少量安排 | 先捕获，再按选择补充日期/时长 | 在冲突、超量和复盘时建议 |
| 轻度计划执行 | 当前/下一项和单一主按钮 | 一句输入即可保存或开始 | 只在明确需要时出现，不常驻 |

## 4. 渐进式添加任务：完整交互规格

### 4.1 入口与第一屏

入口有三种，但都进入同一个 `TaskCapture` 状态机：

- 今日页底部输入栏：默认添加到“待安排”。
- 任务页右上角添加：默认进入收件箱。
- Plan 空档点击：默认带入日期和开始时间，但不强制用户确认全部字段。

第一屏：

```text
接下来要做什么？
[ 写下任务……                         🎙 ]

             [先保存]   [安排到今天]
```

语音路径：点击麦克风 → Android SpeechRecognizer 转文字 → 文本进入同一个输入框 → 用户可编辑 → 应用可以解析出日期/时长建议。语音结果不能直接提交任务或创建提醒。

输入自然语言后的结构化预览：

```text
复习高数第三章，今晚八点开始，大约一小时

识别到：今天 20:00 · 约 60 分钟
[保留] [修改]
```

这是“结构化建议”，不是静默事实写入。失败时保留原文，仍可作为普通任务保存。

### 4.2 逐步问题策略

每一步只问一个当前决策必要的问题；每一步都允许跳过，且草稿持续保存。

#### Step 1：任务内容

- 必填：标题或可识别的描述。
- 可选：语音输入。
- 退出：自动保存为草稿/收件箱，提示“已保存到待安排”。

#### Step 2：用户选择下一步

显示三个互斥方向，不再自动打开一堆字段：

- `现在开始`
- `安排今天`
- `先放着`

#### Step 3：只有需要时补充时间

若选择“安排今天”，先选择：

- `只安排到今天`
- `安排具体时段`
- `设置截止时间`

如果用户只选择到今天，就不追问精确时段；如果选择具体时段，再问开始和时长；如果选择截止，只问截止日期/时间。

#### Step 4：时长用选择而不是空白数字

推荐选项：`15 分钟`、`30 分钟`、`60 分钟`、`90 分钟`、`不确定`。选择“不确定”后允许后续从真实执行记录估算，不要求用户伪造精度。

#### Step 5：情境字段按任务类型出现

- 普通事务：类别和优先级藏在“更多”。
- 课程/学习：可以出现课程、目标、复习/练习类型。
- 固定事项：出现重复规则或固定时间。
- 并行活动：用户明确选择“添加伴随轨道”后才出现音乐、通勤、休息等轨道。

#### Step 6：提交反馈

保存后不弹“任务创建成功”的空洞 Toast，而是明确结果：

- `已保存到待安排`
- `已安排到今天 20:00–21:00`
- `信息不足，先保留任务；稍后可以安排`

### 4.3 编辑已有任务

编辑不复用创建路径的所有步骤；使用详情页中的局部编辑：

- 点标题直接改标题。
- 点时间摘要改日期/时段。
- 点“更多”打开属性抽屉。
- 点执行记录进入日志，而不是在编辑表单里堆叠历史。

这样可以避免用户为了改一个日期再次经过标题、分类、优先级等无关字段。

## 5. 任务详情：列表只看决策，详情看证据

### 5.1 任务详情首屏

```text
< 返回                         …

复习高数第三章
待开始 · 今天 20:00 · 60 分钟

[开始]

下一步
先完成例题 1–3

时间        今天 20:00–21:00
截止        今天 23:00
```

首屏不显示完整描述、所有字段和全部日志。主操作根据状态变化：开始、继续、完成、处理反馈。

### 5.2 可折叠区

- `任务说明`：有内容才展示。
- `更多属性`：类别、优先级、估时、来源、并行轨道。
- `执行记录`：按时间倒序，默认只显示最近一次；可展开全部。
- `画像依据`：显示“来自 5 次同类任务、最近 30 天”，不显示不可靠的泛化评分。
- `建议`：仅在有可解释建议时出现，显示影响范围、理由和接受/忽略。

### 5.3 任务控制台与详情的关系

Android 小屏：任务控制台是列表，点击进入详情。

平板/横屏：使用 Android adaptive list-detail：左侧分组任务，右侧展示选中任务详情；切换任务不重复导航。官方 Android 指南也将 list-detail 定义为列表与详情两个协同 pane，并允许小屏单 pane、大屏双 pane。

## 6. 视觉系统：成熟、安静、有呼吸，但不寡淡

### 6.1 视觉基调

参考 Apple 产品的克制层级和物理感，但不做 iOS 皮肤；使用 Android Material 3 的可访问性、动态窗口和系统返回能力。

关键词：

- **Content-first**：内容和下一步动作优先。
- **Quiet surfaces**：背景中性，容器少而有意义。
- **Editorial rhythm**：标题、正文、时间和状态有明显尺度差异，避免每行都像标题。
- **Soft utility**：有温度的米白/冷白背景、深墨文字、单一青绿色行动色，风险使用橙/红但不满屏着色。

UI Pro Max 这轮检索给出的通用结论是：统一字阶、4/8dp 节奏、避免颜色单独表达状态、Android 触控目标至少 48dp、底部导航不超过 5 项、表单采用渐进披露。这里采用这些可验证规则，但不直接照搬它检索出的偏营销型“Product Demo”模式，因为 Repland 是日常工具，不是落地页。

### 6.2 色彩令牌

建议以语义令牌而不是页面硬编码：

| 令牌 | 浅色建议 | 用途 |
| --- | --- | --- |
| `canvas` | 温和的近白/纸白 | 页面底色，不使用渐变 |
| `surface` | 白色或轻微偏色 | 仅用于主卡、抽屉和详情容器 |
| `ink` | 深墨绿黑 | 标题和正文 |
| `muted` | 中性灰绿 | 辅助说明和次要时间 |
| `accent` | 低饱和青绿 | 主按钮、当前项、选中状态 |
| `warning` | 琥珀橙 | 需要用户确认、接近超量 |
| `danger` | 深红 | 冲突、不可行、明确错误 |
| `success` | 稳定绿 | 已完成/已确认，必须同时有文字或图标 |

避免：彩色背景卡片、每个任务类别一种高饱和色、用绿色/红色单独传达状态、用渐变营造“AI 感”。

### 6.3 组件规格

- 顶部栏：64dp 左右，标题 20–22sp；不使用 40sp 的大标题占满首屏。
- 页面水平内边距：手机 20dp，横屏/平板按窗口宽度增加，但保持可读文本宽度。
- 任务行：最小高度 64dp，触控区域至少 48dp；普通列表行无厚重阴影。
- 主卡：圆角 16dp，最多一张主卡；列表行使用分割线、轻微容器或分组背景。
- 状态图标：一套 Material 线性图标，24dp 视觉大小，外围点击区 48dp。
- 芯片：只表示一个事实，如“待安排”“今天”“高”；不把一整段状态句塞进芯片。
- 按钮：每个区域一个主动作，次要动作改为文字按钮或更多菜单。
- 空状态：一句事实 + 一个动作，不放产品宣传文案和装饰图表。

### 6.4 字阶

建议固定为：`12 / 14 / 16 / 18 / 22 / 28sp`，并使用 Material 3 typography 映射。标题和正文的层级由大小、字重、颜色同时决定；不能把所有文本都设置为 `titleMedium`。

## 7. 动效：把运动用来解释变化，而不是装饰

参考 Emil Kowalski 的设计工程原则：动画必须回答“发生了什么变化”，进入快、退出更快、可中断、不给用户制造等待。使用 Android Compose 原生动画和 Material motion，不把所有列表都做成入场动效。

### 7.1 动效 token

| 场景 | 动作 | 建议 |
| --- | --- | --- |
| 任务行完成 | 状态控件轻微收缩/勾选，标题降低强调 | 160–220ms，保持行高不跳动 |
| 添加任务逐步推进 | 下一问题替换当前问题，保留内容位置 | 180ms fade + 8dp shared-axis，禁止整页飞入 |
| 底部抽屉 | 从底部进入，带系统手势可中断 | 220–300ms，spring 或 Material 标准曲线 |
| 时间块移动 | 拖拽期间跟手，落点有短暂高亮 | 120ms 落位确认；提供非拖拽按钮替代 |
| 负载变化 | 数字淡变，不做大面积进度条动画 | 160ms |
| 任务详情展开 | 内容沿原位置展开 | 180ms；只对用户主动展开响应 |
| 草案变更 | 被影响的任务轻微标记，不自动逐个飞动 | 200ms 标记出现；不使用持续呼吸动画 |

### 7.2 动效纪律

- 重要操作必须在 80–150ms 内给出按压反馈。
- 支持 reduced motion：去掉非必要位移和 stagger，只保留状态变化。
- 不通过动画隐藏数据变化；动画结束后信息必须稳定。
- 不对每张 TaskCard 使用统一入场 stagger；任务页是工具，不是营销页面。
- 批量更新时仅显示一次结果反馈，避免十几项同时跳动。
- 键盘、语音、系统返回和无障碍焦点都要走同一状态机，动画不能成为唯一导航方式。

## 8. 前后端与状态设计：为 Workflow/Agent 留根，但不让它们绑架 UI

### 8.1 UI 状态与领域事实分离

建议新增 UI 层状态模型，不直接让 Composable 拼接所有领域字段：

```kotlin
data class TaskRowUiModel(
    val id: String,
    val title: String,
    val timeLabel: String?,
    val statusLabel: String,
    val status: TaskVisualStatus,
    val hasDescription: Boolean,
    val primaryAction: TaskPrimaryAction?,
)

data class TaskCaptureState(
    val input: String,
    val stage: CaptureStage,
    val parsedSuggestions: List<CaptureSuggestion>,
    val destination: CaptureDestination,
    val draft: TaskDraft,
)
```

这样“列表只看摘要、详情看完整事实、创建只显示当前阶段”不会继续把条件判断堆在 `ReplandApp.kt`。

### 8.2 创建流程状态机

```text
Idle
  -> Capturing
  -> ParsedSuggestion (可选)
  -> ChooseIntent
       -> SaveToInbox
       -> StartNow
       -> ScheduleDay
  -> AskDuration (仅选择具体安排时)
  -> AskTimeOrDeadline (按选择出现)
  -> ReviewDraft
  -> Saved
```

每个阶段都可以：

- 保存草稿；
- 后退一步；
- 跳过非必填问题；
- 回到原始输入；
- 无 Agent、无网络时正常完成。

### 8.3 “任务总览台”数据投影

控制台不修改任务实体，它是一个投影：

- `NeedsAttention`：待确认、冲突、逾期、连续延期。
- `Today`：有今天日期或今天时间段的任务。
- `Inbox`：没有日期/时段的活跃任务。
- `Upcoming`：未来有安排的任务。
- `Completed`：完成/取消/放弃，默认折叠。

投影由确定性规则生成；Agent 可以给出“建议分组/建议排序”，但 UI 必须把建议标为建议，并允许用户恢复默认排序。

### 8.4 Profile 反哺的可见方式

画像不应该直接操控界面而不解释。画像总结只通过三种轻量方式反哺：

1. 默认值：例如用户同类任务通常 45 分钟，下一次显示为可编辑建议。
2. 风险提示：例如“最近 5 次同类任务平均比预计多 20 分钟”。
3. 入口顺序：用户常用“先保存到待安排”，下次把它作为主按钮，但可随时切换。

画像卡不常驻首页；用户从任务详情或“我的节奏”主动查看证据。所有总结都带样本量、时间范围和来源，不展示无根据的“效率分数”。

## 9. 实施路线：按体验链路重做，不按组件数量堆功能

### Phase 1：重做默认工作面

1. 把 `TodayScreen` 改为 Now + 下一项 + 需要处理 + 收件箱入口。
2. 删除解释型时间线卡的常驻展示，只在无真实数据时提供极简空状态。
3. 把 `TaskCard` 拆成 `TaskRow`，完成/开始动作保持可达。
4. 用 Material 图标替换自绘 `TabGlyph`，建立四个导航入口的语义一致性。
5. 继续复用现有任务、计划和执行日志数据，不改数据库。

验收：打开应用 3 秒内能找到下一项；任务列表一屏可扫描至少 6–8 行；空状态不超过一个主动作。

### Phase 2：渐进式创建

1. 新建 `TaskCaptureScreen` 或底部 `TaskCaptureSheet`，替换全量 `TaskEditorDialog` 的创建路径。
2. 建立 `TaskCaptureState` 和本地草稿保存。
3. 接入文本、语音、自然语言结构化建议，但保持手动编辑和保存。
4. 让今日/任务/计划三个入口复用同一个状态机，只注入默认 destination。
5. 编辑已有任务改为详情内联编辑与局部抽屉。

验收：只输入标题即可保存；用户不选择时间不被阻塞；从 Plan 空档创建会带入日期但不要求所有字段；返回不会丢草稿。

### Phase 3：任务总览台与自适应

1. 加入快捷视图和分组折叠。
2. 加入搜索、少量排序和稳定的空状态。
3. 小屏 list-detail 单 pane，大屏/横屏双 pane。
4. 让任务详情支持局部编辑、执行反馈和日志折叠。

验收：同一任务在 Today/Tasks/Plan/详情的标题、状态、时间一致；横屏不产生重复的第二份任务状态；系统返回路径可预测。

### Phase 4：成熟体验与智能参与

1. 将冲突、超量、连续延期变成上下文建议。
2. Workflow 负责捕获 → 解析 → 生成草案 → 用户确认 → 写入版本 → 记录日志的编排。
3. Agent 负责多方案建议、解释和总结，不成为事实写入者。
4. 接入画像反哺的可编辑默认值和带证据风险提示。

验收：关闭 Agent 或断网时，Phase 1–3 的闭环全部可用；打开 Agent 后只增加建议和解释，不改变用户看见的事实来源。

## 10. 本轮设计自省

### 自省 1：是不是又把“安静”做成了“空”？

风险：删除大卡片后，页面可能只剩空白和几个按钮。

修正：安静不等于空。真实安排存在时，Now 卡、负载摘要、下一项和待处理区必须有层级；没有真实数据时不制造装饰数据。信息少是事实，不是需要用宣传卡填满的缺陷。

### 自省 2：渐进披露会不会把效率藏得太深？

风险：重度用户每次都要点击很多步。

修正：保存到收件箱保持一步完成；重度用户可以启用“快速完整创建”或直接使用自然语言/语音，一次解析出多个可编辑建议。渐进披露只隐藏非当前必要字段，不隐藏高级用户的快捷路径。

### 自省 3：任务总览台会不会重新变成大仪表盘？

风险：为了满足“看全局”，把所有分组、指标和统计重新堆上去。

修正：总览台的任务是分流，不是展示全部真相。默认只展开一个需要处理分组；其他分组折叠，负载作为行级摘要；完整画像和历史另有入口。

### 自省 4：参考 Apple 会不会变成模仿 iOS？

风险：过度使用大留白、圆角和半透明，失去 Android 的效率。

修正：借鉴 Apple 的克制、层级和动效连续性；使用 Android 原生返回、自适应 list-detail、Material 触控标准和系统语义，不伪装成 iOS。

### 自省 5：Agent 是否会重新把界面复杂化？

风险：在每个页面都塞一个“问问 AI”。

修正：Agent 只在有上下文的任务详情、计划差异和每日复盘出现；空闲时不常驻聊天按钮。每个建议显示影响范围、来源和接受/忽略动作。

## 11. 对抗性审查

### 反方意见 A：竞品已经有时间线，我们没必要再做任务总览台

回应：时间线解决“什么时候发生”，任务总览台解决“现在要处理哪类任务”。如果只有时间线，无日期任务、逾期任务和待确认反馈会被淹没；如果只有列表，用户又无法理解可执行时间。两者是两个不同的决策面，必须通过同一任务投影保持一致。

### 反方意见 B：全量表单至少不会丢字段

回应：不丢字段不代表能完成任务。移动端首录入的最大风险是放弃和伪造。字段仍然存在于详情和局部编辑；创建阶段只把能改变当前路径的字段前置。数据完整性由草稿和领域校验保证，不由首屏字段数量保证。

### 反方意见 C：减少颜色和卡片会让比赛展示不够“惊艳”

回应：比赛演示需要的是一条能被理解的惊艳路径，而不是每屏都高饱和。真正可展示的瞬间是：一句语音变成可编辑任务，用户选择“今天”，系统给出时间建议，用户在时间轴确认，执行后真实反馈反哺下一次估时。视觉克制会让这些变化更突出。

### 反方意见 D：多模式会增加实现成本

回应：如果把模式写成三套页面，成本会失控；本方案只改变 UI 投影、默认入口和信息密度，领域模型统一，创建状态机统一，测试可以以同一状态矩阵覆盖三种模式。

### 反方意见 E：如果用户就是想看全部信息怎么办？

回应：提供“全部详情”而不是“首屏全量”。任务详情、计划周视图、画像证据和历史日志都可以看；默认工作面应为高频决策优化，而不是为极少数查看全量的时刻牺牲每天的可用性。

### 11.1 交付前硬性检查

- [ ] Today 首屏没有常驻产品说明卡。
- [ ] 任务列表默认是分组紧凑行，不是完整详情卡。
- [ ] 新任务只输入标题即可保存。
- [ ] 日期、时长、分类、优先级按选择逐步出现。
- [ ] 语音结果进入可编辑文本，不能直接写入不可逆事实。
- [ ] 任务总览台能在不打开详情的情况下完成开始/完成/延期等主动作。
- [ ] 详情页能查看完整字段，但默认折叠描述、画像和历史。
- [ ] 计划时间、截止时间、实际耗时分别展示，不相互伪装。
- [ ] 状态不只靠颜色表达；图标和文字可读。
- [ ] 所有图标按钮触控区至少 48dp，有无障碍语义。
- [ ] 375dp 小屏、横屏、平板/折叠屏、深色模式、加大字体、减少动效均有验证。
- [ ] 无 Agent、无网络时核心路径仍然可用。
- [ ] 新的 Agent/Workflow 建议不会绕过用户可见的草案和日志。

## 12. 下一步建议

本轮建议先只实现 Phase 1 和 Phase 2，不要马上继续加画像图表、更多 AI 按钮或更多统计。原因不是限制能力，而是先验证新的信息架构是否真的降低了操作负担：

1. 先把今日页和任务页改成“下一步 + 分组列表”。
2. 再把添加任务改成渐进式流程。
3. 用模拟器测试三类用户从语音/文本输入到开始执行的完整链路。
4. 通过真实使用记录观察用户是否会主动补充时长、是否频繁从待安排转为今天、哪些字段真正改变计划。
5. 再决定哪些字段适合成为 Workflow 自动补全，哪些适合由 Agent 提供建议。

本报告的核心判断是：**先把复杂能力藏到正确的层级里，再把智能能力放到正确的时机里。** 这会让 Repland 的能力上限更高，而不是更低。
