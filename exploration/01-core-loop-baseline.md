# 核心链路基线

> 状态：事实基线  
> 目的：在讨论 Agent 化之前，明确哪些能力必须先由传统、本地、确定性的应用链路跑通。

## 1. 当前核心闭环

```text
录入任务
  → 补充时间与硬约束
  → 生成本地计划草案
  → 用户编辑 / 确认 / 丢弃
  → 形成当前计划版本
  → 按已确认计划执行
  → 用户提交真实反馈
  → 形成调整草案
  → 用户再次确认
```

这个闭环本身不依赖 Agent，也不应该依赖远程模型。Agent 只能改善输入理解、取舍建议、解释和总结，不能成为闭环成立的前提。

## 2. 当前代码事实

| 领域 | 当前结构 | 基线判断 |
| --- | --- | --- |
| 任务 | `Task`、`TaskExecution`、`TaskRepository`、`RoomTaskRepository`、`TaskViewModel` | 生命周期和追加式执行日志已经有较完整基础 |
| 时间 | `TimeArrangement`、`TimeRepository`、`RoomTimeRepository`、`TimeViewModel` | 周期时间块、日期例外和课表导入已有基础 |
| 计划 | `Plan`、`PlanViewModel`、`PlanRepository`、`RoomPlanRepository` | 本地排程、草案、确认、历史/恢复已形成主链路 |
| 提醒 | `Reminders`、`LocalReminderScheduler`、Receiver | 应严格从已确认计划派生，不能从草案派生 |
| AI 边界 | `PlanningAgent`、`AiAdvisorContract`、`PlanningAgentViewModel` | 已有请求预览、输出验证和 NoOp 降级边界 |
| 数据 | Room 数据库、JSON 导出、清除流程 | 本地优先和可带走数据是产品约束 |
| UI | `ReplandApp.kt` 集中承载四个入口和大量对话框 | 可运行，但跨模块流程编排集中在 UI 层，后续是架构调整重点 |

## 3. 非 Agent 基础链路验收线

### 3.1 任务链路

- 最少信息可以快速保存任务。
- 缺少时长或可用时间时，任务进入“待安排”，而不是被拒绝或被假设安排。
- 开始、完成、部分完成、延期、取消、替换和恢复都由用户确认。
- 完成反馈至少保留“完成了什么”；实际时长、进度和结果可以补充。
- 任务详情可以按时间查看执行记录，并支持更正但不覆盖原记录。

### 3.2 计划链路

- 本地算法能够综合任务、截止日期、预计时长、可用时间和硬约束。
- 信息不足时只给出任务顺序，不伪造具体时段。
- 新计划先形成草案，不影响当前计划、提醒和执行状态。
- 用户可以编辑草案、确认草案或丢弃草案。
- 每次确认产生新版本；回退是创建新当前版本，不删除历史。

### 3.3 执行和重规划链路

- 已结束工作段进入“待确认”，系统不推断完成或失败。
- 用户反馈后只生成调整草案，不静默挪动剩余工作。
- 容量不足、截止不可达、硬约束冲突和信息不足必须有可解释原因。
- 用户可以在继续、拆分、改期、降低目标和放弃之间作出选择。

### 3.4 系统链路

- 提醒只来自已确认计划。
- 计划确认、修改、回退和清除时，提醒能够同步更新或撤销。
- 没有 AI、没有网络或 AI 输出无效时，核心链路仍然可用。
- 数据导出和本地清除不会被 Agent 或自动流程隐式触发。

## 4. 当前最值得先修的基础问题

这些问题不应该等 Agent 来掩盖：

1. `ReplandApp.kt` 同时处理导航、草案生成触发、任务详情、反馈弹窗、时间约束编辑、AI 工作流和数据管理，流程知识过度集中在 UI 组合层。
2. `PlanViewModel` 接收较多由 UI 拼装的规划输入，业务流程入口还没有形成清晰的应用层用例。
3. “任务变化 / 时间变化 / 反馈变化 → 计划需要更新 → 生成草案”已经是重复出现的业务模式，但目前缺少统一的失效原因和流程状态模型。
4. 当前数据模型能保存计划和日志，但对“某次流程为什么产生某个草案、用户做了什么决定、影响了哪些对象”的表达仍然偏弱。
5. UI 需要继续明确区分当前计划、未确认草案、待确认工作段和历史版本，否则后续引入 Agent 后容易出现越权感。

## 5. 当前阶段的定义

当前阶段不是“先把 Agent 接上”，而是：

> 把确定性规则、用户决策和数据历史做成可信的产品底座，再把 Agent 放到信息不足、需要权衡、需要解释的地方。
