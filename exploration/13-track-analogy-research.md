# 轨道式日程专项调研与设计补充

日期：2026-09-26

## 结论先行

我们要借鉴的不是音乐软件的皮肤，而是它的对象模型：

> 先创建可复用的内容对象，再把对象编排到时间轴和轨道上。

日程中的“事件”对应音乐软件里的 Clip；日程中的“轨道”对应 Track；某个日期和时间上的一次安排对应 Arrangement Instance；用户实际执行对应 Playback / Performance Log。

这样可以解决三个问题：

1. 创建事件时不用提前知道日期和轨道。
2. 同一事件可以复制到多个日期，或者放入不同轨道。
3. Agent 负责建议编排，用户仍然拥有最终确认权。

## 竞品与相关实现

### Ableton Arrangement / Session

[Ableton Arrangement View](https://www.ableton.com/en/manual/arrangement-view/)把音频或 MIDI 内容表示为轨道上的 Clip。官方文档明确支持把 Clip 拖到另一个时间位置或轨道，并将轨道上下堆叠、排序和扩展。Arrangement 负责线性时间编排，Session 则更适合从多个 Clip 中试演和组合。

可迁移到 Repland 的机制：

- 事件对象先存在于“事件库 / Inbox”，时间轴只是它的一次编排。
- 拖动事件同时改变日期、时间和轨道，但不改变事件本体。
- 日视图是 Arrangement；事件库是轻量 Session。
- 同一事件支持“复制到这里”和“移动到这里”两个不同动作。
- 轨道需要有独立的折叠、排序和关注状态，不能只是一块颜色。
- 时间轴顶部需要一个缩略概览条，用来快速跳到早晨、下午或晚间。

### GarageBand 的 Region / Loop 思路

[GarageBand iPhone 用户指南](https://help.apple.com/pdf/garagebandiphone/en_US/garageband-iphone-user-guide.pdf)把录音、音频区域和 Loop 当成可放置到轨道上的内容，用户可以从浏览器把 Loop 或音频拖进轨道。

可迁移到 Repland 的机制：

- 事件对象可以有“模板内容”：例如“英语听力 30 分钟”“力量训练 45 分钟”。
- 从事件库拖出时，拖出的不是一次性文本，而是一个可复用实例。
- 事件详情中的描述、目标和复盘记录属于对象；日期、轨道、开始时间属于实例。
- 快速复制不是复制全部执行历史，只复制计划属性。

### Unity Timeline 的 Track List / Marker

[Unity Timeline Track List](https://docs.unity.cn/Packages/com.unity.timeline%401.8/manual/trk-list-overview.html)把轨道作为可管理的结构，支持新增、选择、复制、删除、锁定、静音和排序；Timeline 还把 Marker 作为独立的时间点信息。

可迁移到 Repland 的机制：

- 轨道头应有收起、锁定和专注三种轻操作。
- 锁定轨道后，Agent 可以建议但不能直接改动该轨道中的安排。
- 轨道可以排序，而不是只能按创建顺序排列。
- 时间轴需要“标记点”：考试、截止日期、出门、睡觉等不一定有持续时间，但会影响附近安排。
- 事件块和标记点不能使用同一种视觉形态，避免用户误以为标记是任务。

### Structured 的 Inbox 与多层时间视图

[Structured 入门文档](https://help.structured.app/en/articles/380546)说明它以日时间线为主，并用 Inbox 保存还没有具体日期或时间的任务；任务可以从 Inbox 拖到时间线。其产品页也强调日、周、月视图的连续切换。

可迁移到 Repland 的机制：

- 事件库是默认入口，不是错误状态。
- 未安排事件不显示为“缺失信息”，而显示为“待编排素材”。
- 日视图负责行动，周视图负责平衡，月视图负责趋势。
- 周、月视图不复制日视图的所有细节，而是逐级降低信息密度。

### Sunsama 的计划时间与实际时间

[Sunsama Planned and Actual Times](https://help.sunsama.com/docs/usage-guides/tasks/planned-and-actual-times/)区分任务的计划时间和实际工作时段，实际时间来自工作会话，而不是要求用户在任务完成时填写一张表。

可迁移到 Repland 的机制：

- 排程实例保存计划开始、计划结束和计划轨道。
- 执行日志保存真实开始、真实结束和中断次数。
- 完成动作保持轻量，复盘在用户空闲时补充。
- Agent 可以依据计划与实际的偏差调整未来估计，但不直接重写历史。

## 游戏设计可以借鉴的部分

这里不是复制游戏界面，而是借鉴游戏对状态和反馈的处理方式：

### 1. Now / Next / Later

游戏很少要求玩家同时理解全部事件，而是明确当前、下一个和稍后。日轨道可以在当前时间线上增加三种视觉状态：

- Now：当前正在执行，使用细微的动态进度线。
- Next：下一个可行动事件，提供开始入口。
- Later：已安排但暂时不需要关注的事件，降低对比度。

### 2. Cooldown / Recovery

任务完成后不一定马上进入下一个任务。可以把恢复、通勤、切换成本视为轨道之间的“冷却区”，由系统根据用户历史自动建议，而不是把每一段都强制变成任务。

### 3. Quest / Objective / Encounter

一个长期目标可以拆成：

- Objective：目标事件，例如“准备考试”。
- Quest：可执行事件，例如“整理错题”。
- Encounter：一次排程实例，例如“周三 19:30–20:15 放到学习轨道”。

这会让 Agent 更容易判断自己是在创建目标、拆解事件，还是安排一次执行。

### 4. Checkpoint / Marker

考试、出发、课程开始、睡眠等事件可以是 Marker，而不是普通任务。Marker 只占据一个时间点，却能影响前后事件的缓冲和优先级。

### 5. Pause / Resume / Replan

“暂停”不等于“完成”，“重新安排”不等于“删除”。用户临时离开任务时，应保留当前执行上下文，让系统以后可以从暂停位置恢复或生成新的排程实例。

## Repland 的具体交互规格

### 事件库

- 入口：日视图顶部的“事件库”抽屉，或首页语音 / 对话创建后自动进入。
- 默认分组：未安排、最近使用、模板、重复事件。
- 卡片只显示标题、估计时长、类别和最近一次使用日期。
- 不显示完整描述、完成内容和历史记录，避免事件库变成任务详情列表。
- 长按事件卡进入拖动状态；点击只进入事件详情。

### 拖动到轨道

- 拖动时显示事件卡的半透明影子。
- 轨道头高亮显示接受区。
- 时间轴以 15 分钟吸附为默认，支持切换 5 / 30 分钟。
- 松手后先生成预览实例，不立即写入数据库。
- 预览实例出现“放置 / 复制 / 取消”轻确认条，避免误拖造成不可逆修改。
- 与固定课程冲突时不阻止拖动，显示冲突层：继续、缩短、换轨道、让 Agent 建议。

### 轨道控制

- 拖动轨道头调整顺序。
- 折叠轨道只隐藏事件块，不删除安排。
- 锁定轨道后 Agent 和自动排程不能修改其中的实例。
- 关注轨道只提高视觉层级，不过滤其他轨道，避免用户失去全局上下文。
- “静音”在日程中对应关闭提醒，而不是隐藏安排。

### 周视图

- 七列或横向七卡，显示每天事件数量、总计划时长、轨道覆盖数和冲突数。
- 支持拖动事件从一天复制到另一天。
- 点击某一天进入日轨道；不在周视图中编辑复杂描述。
- 顶部显示本周负载波形：不是折线图，而是每一天的计划密度条，便于快速识别过载。

### 月视图

- 只表达密度、节奏和关键 Marker。
- 颜色点代表轨道类别，数字代表事件总数。
- 重要日期显示 Marker 标签，例如“考试”“旅行”“截止”。
- 点击日期进入日视图，长按日期进入“复制一组事件到这一天”。

## 数据与 Agent 边界

建议最终拆成四个实体：

```text
EventObject
  事件本体，可复用

Track
  用户定义的节奏轨道

ScheduleInstance
  EventObject + date + start + end + trackId

ExecutionRecord
  实际开始、结束、暂停、完成、复盘
```

Agent 只提出 EventObject、ScheduleInstance 或 Track 的草案；用户确认后才落库。执行状态和历史记录不交给 Agent 直接覆盖。

## 最终设计判断

音乐软件提供“对象—轨道—时间轴”的结构，游戏提供“当前—下一个—恢复—标记”的节奏反馈，日程竞品提供 Inbox 和日 / 周 / 月缩放。三者结合后，Repland 的核心不应是任务清单，而应是一个可以被用户和 Agent 共同编排的个人时间编曲台。
