# Repland 整体产品与系统设计方案（能力优先版）

> 状态：探索设计稿 v1.0 · 2026-09-25。本文是目标设计，不代表代码已实现。现有事实以仓库代码为准；旧产品边界是可质疑的历史决策，不是本方案的能力上限。

## 0. 决策摘要与阅读方式

Repland 要解决的不是「把任务塞进日历」，而是用户在任务、时间、精力、目标不断变化时，仍能低成本地得到一个可执行、可调整、可信的下一步。第一阶段先把不依赖 Agent、远程服务或自动化的完整链路做强；但领域对象、决策记录、操作接口与前端反馈从第一天就支持未来的自动化和可授权代理。

本版修正此前探索文件中的过早收口：**不以“当前 MVP 不做”推导“产品不该做”**。重复任务、步骤/目标、外部日历、跨端同步、自然语言入口、自动重排、主动建议、Agent 执行都保留为目标能力；进入顺序由用户价值、依赖和可验证的风险决定。用户可选择手动、辅助、委托不同操作方式，不把统一的「一律确认每一步」强加给所有人。只有不能由软件诚实观察到的现实结果（例如用户是否真正完成学习）才不应被系统冒充为事实。保密、权限、支付/清除等不可逆动作仍需工程级防护，这不等于冻结产品能力。

### 0.1 本文的三种陈述

| 标记 | 含义 | 例子 |
| --- | --- | --- |
| **现状** | 已在代码或文档中找到 | 单设备 Room、四个入口、计划草案和版本、本地提醒、NoOp Advisor |
| **目标** | 本方案明确建议实现 | 持久草案、可配置自动化、计划差异、步骤/依赖、可选同步 |
| **待验证** | 设计假说，不应伪装成用户结论 | 大一新生是否更愿意打开“今日”而非“收集箱” |

### 0.2 用户价值北极星与约束重排

1. **收集不费力**：有想法就能记，含糊信息之后再补；语音/分享/文本可逐步接入。
2. **现实可见**：任务、明确承诺、可用时间、休息和外部事件放进同一时间模型；容量不够时直说。
3. **下一步清楚**：打开应用即知道现在可做什么，以及为什么。
4. **变化可承受**：新任务、延期、外部安排、实际耗时变化触发局部重算；用户知道影响，不必从头规划。
5. **控制可调节**：新手可看建议并确认；熟练用户可为指定范围设置自动化策略；高后果操作仍有审计和撤销。
6. **系统有记忆但不贴标签**：基于可更正的反馈校准估时和节奏，而非“效率分数”。

旧文档中“所有计划修改必须逐项确认”“所有冲突绝不可自动处理”等规则，本文改写为**默认策略**而非永久产品天花板。委托能力需有作用范围、阈值、预览或事后通知、撤销窗口、日志与停止开关。验证一旦证明过度弹窗阻碍用户行动，允许更主动的模式。阶段一仍然实现手动闭环，不靠未来能力遮掩基础问题。

## 1. 依据、现状与关键落差

依据：仓库 [README](../README.md)、[术语与旧边界](../CONTEXT.md)、[竞品报告](../docs/COMPETITOR_DESIGN_BOUNDARIES.md)、[探索基线](01-core-loop-baseline.md)、[传统工作流盘点](02-traditional-workflow-audit.md)、[Agent 候选](03-agent-workflow-candidates.md)，以及本轮检查的 `Task.kt`、`Plan.kt`、`PlanViewModel.kt`、`PlanDao.kt`、`ReplandApp.kt`。竞品报告研究了 Todoist、TickTick、Structured、Motion、Sunsama 的公开官方材料；可用其发现问题，不能把它当用户调研的替代。

| 维度 | 现状 | 目标差距 |
| --- | --- | --- |
| 产品 | Android 中文本地优先，四个导航入口；计划/反馈主链可运行 | 完成从首次打开到周期性复盘的连续体验，避免“功能在但入口散” |
| 任务 | 最低输入路径存在；`TaskDraftValidator` 仍要求名称、1–30 天预计周期，并阻止过去截止日 | 标题或描述任选其一即可保存；预计周期可空；逾期是可处理状态而非数据无效；高级任务结构可演进 |
| 计划 | 本地 30 分钟粒度、未来 30 天窗口；可用时间明确输入后才精确排程 | 规划视野和粒度可配置或多尺度；长期目标不被 30 天截断，近期视图仍保持清晰 |
| 草案 | `PlanViewModel` 的草案在内存，进程终止可能丢失；接受异常没有清晰错误状态 | 持久保存、输入快照与过期检测、恢复编辑、可见失败与重试 |
| 版本 | Room 事务切换当前计划；锁定开关可直接原位更新当前版本段 | 版本语义统一：计划、锁定、手动调整的变更由明确操作生成新修订或附加决策日志 |
| 提醒 | 已确认计划派生的本地提醒，用户需授权通知 | 可靠重算、去重、与新版本对账；交互上解释“设备可能延迟提醒” |
| UI | 单个 `ReplandApp.kt` 汇集多个页面和流程；大量对话框，底栏用文字首字 | 按旅程与组件拆分；任务/时间/计划互相可达；语义图标和一致状态语言 |
| 智能 | 有类型化 PlanningAgent、请求预览和 NoOp Advisor；无真实后端与模型 | 先稳本地，再接受控网关；最终允许用户定义的、可解释的代理权限与工作流 |

当前 UI 代码的设计工程对照（不是已经完成的改动）：

| Before | After | Why |
| --- | --- | --- |
| `ReplandApp.kt` 内四个主页面与大量弹窗/流程并列 | 页面模块化，跨对象流程移入 application 用例 | 避免一次视觉调整牵动计划规则与导航 |
| 底部导航用标签首字作图标 | 同一矢量图标家族 + 常驻文字标签 | 让入口在中文语境下可辨、可朗读 |
| 长计划草案塞在 `AlertDialog` | 差异摘要 + 全屏/大 sheet 编辑 | 小屏阅读和复杂编辑不再嵌套滚动 |
| 当前主题仍以模板紫色为主，字阶较少 | Repland 语义色/字阶/明暗模式令牌 | 让行动、候选、冲突与信息密度形成可维护语言 |

**待验证用户画像**：第一批用户假定为课程、作业、社团、生活事务交错的大学新生；“低规划负担”是方向，不是已经量化的事实。通过 6–8 人情境访谈、7 天日记、原型任务测试验证：首次建计划耗时、次日回到计划的比例、冲突时能否理解建议、多少确认属于干扰。不得仅用完成率衡量成效。

## 2. 从用户任务反推功能全景

### 2.1 对象模型：不要让“任务”吞掉所有概念

| 对象 | 语义 | 最低字段与后续演进 |
| --- | --- | --- |
| Capture/收集项 | 尚未澄清的输入 | 原文、来源、创建时间；可转任务、事件、目标、备忘或丢弃 |
| Task/任务 | 用户要推进的结果 | 标题/描述、状态、截止与重要性；可增步骤、依赖、重复规则、目标关联、分工 |
| Commitment/承诺事项 | 已知时间被占用的现实事件 | 起止、时区、来源、强度；课程、会议、休息都可表达，但各有默认行为 |
| Availability/可用窗口 | 用户愿意安排工作的时段 | 周模板、例外、偏好时段、信心；“未声明”不等于“全天空闲” |
| WorkUnit/工作单元 | 可放入时间轴的任务份额 | 所属任务、预计时长范围、先后关系、可分割性 |
| Session/执行段 | 具体日时的安排或已执行记录 | 计划起止、实际起止/耗时、状态、来源、锁定级别 |
| Plan/计划 | 指向当前安排的版本化视图 | 范围、版本、输入签名、原因、差异、作者/规则来源 |
| Proposal/候选变更 | 尚未生效的方案 | 候选操作集合、影响集、成本/收益/冲突、过期依据 |
| Policy/授权策略 | 用户对自动操作的选择 | 动作、对象范围、时间范围、阈值、通知方式、撤销与暂停 |
| Evidence/校准证据 | 从用户反馈与系统观测得到的可检查线索 | 来源、时间、可信度、可更正关系；不等于人格判断 |

第一版不必把全部对象表一次建齐，但 API 和命名要避免把“课程=任务”“草案=当前计划”“建议=执行事实”写死。`Task` 先可继续承载简单任务；引入 `WorkUnit`/`Commitment` 时做增量迁移，保留旧 ID 映射。

### 2.2 功能矩阵：完整能力，不按旧 P0/P2 排除

| 能力域 | 完整目标链路 | 第一落点 | 后续增强/依赖 |
| --- | --- | --- | --- |
| 收集 | 文本、分享、语音/扫描 → 识别 → 澄清 → 保存 | 极速文本与待整理箱 | Android Sharesheet、语音输入、通知快捷添加、Agent 解析 |
| 任务组织 | 分类、截止、重要性、预计时长、步骤、依赖、重复、目标关联、附件 | 简单任务及可选高级字段 | 重复生成器、依赖图、目标路线图、文件存储 |
| 时间模型 | 周模板、日期例外、课表导入、日历事件、休息、专注偏好 | 本地手填与 PDF 预览 | 日历权限/外部双向连接、时区同步、冲突源治理 |
| 规划 | 队列排序、负载测算、多候选排程、长期/近期视野、手动放置 | 本地可解释规划 | 情景比较、增量优化、策略自动排程 |
| 执行 | 今日下一步、时间轴、专注、快速反馈、部分完成、改期 | 今日行动与反馈 | Widget、快捷操作、可选计时、穿戴设备 |
| 复盘 | 实际与预计、未完成原因、明日建议、可更正证据 | 轻量日回顾 | 周回顾、估时校准、长期目标偏差 |
| 控制与恢复 | 变更预览、计划版本、撤销、更正、导出/导入、恢复 | 版本/导出强化 | 可选同步、冲突合并、跨设备恢复 |
| 智能与自动化 | 自然语言理解、冲突比较、授权重排、通知摘要、流程模板 | 不依赖 Agent 的用例接口 | 受控网关、策略中心、工具调用、可暂停代理 |

“第一落点”表示实现顺序，不表示产品能力被否决。要敢于将竞品已验证的低摩擦体验纳入路线，但是否值得做由实测用户频率/价值决定，不能因为竞品有就机械复制。

## 3. 端到端用户旅程与精确定义

### 3.1 首次使用：60 秒内产生价值

欢迎页只回答“这会帮我做什么”；不把课表、通知、账号或 AI 许可放在入口前。用户输入一句任务或目标后立即进入收集箱/任务详情；系统显示可补字段，不知道时间时先给有序清单、容量未知提示和“补充可用时间”动作。首次计划可以手动排序并保存，不能因缺课表而空屏。通知权限在首次设提醒时请求；日历/文件访问在用户触发导入时请求。可选“导入课表”作为加速路径，但跳过同样可用。

### 3.2 捕获 → 澄清 → 安排

输入 `下周三交数据库作业，先看资料，大概两晚`：本地阶段保存原文，用户可点选“截止日/估时/步骤”建议；Agent 阶段可解析为候选结构，每一字段注明“用户原文/推断/不确定”。保存不因字段缺失失败，系统将未定事项放在“待安排”，并只追问最影响规划的一件事。已明确的用户字段永远优先于推断。任务有期限无时长时可进入排序但不能精确容量预测；有时长无期限可在当前规划视野内安排。

### 3.3 时间输入 → 候选计划 → 生效

用户选周模板/课表 PDF/日历授权/临时例外；导入要展示解析表、冲突、源与不确定项，可逐项改正再写入。规划器读取一致快照，先找不可放置冲突与容量缺口，再生成至少一个基线方案；对多目标取舍可产生「最早完成」「保护休息」「减少切换」等候选。草案页按**新增、移动、保留、冲突、未安排**显示差异，支持列表与时间轴编辑。手动微调可先在草案中完成，提交后成为当前计划；若输入已变化，提示刷新差异而非覆盖新事实。后续可启用仅在授权范围内的小变更自动生效策略。

### 3.4 今日 → 执行 → 反馈 → 重规划

今日首屏呈现现在可做/下一步、离开始或截止还有多久、今日可用与已承诺负载、待确认变化。开始只代表用户开始或时间段已到的计划状态；完成须有用户反馈或可信外部证据，证据来源/适用范围可核查；若未来用户明确授权特定来源与场景，允许基于可靠证据自动记录为可撤销事实。工作段结束提供「完成了这一段 / 部分完成 / 没做」；任务级完成与段完成分离。反馈可先一键记录，再补时长、成果、障碍。剩余工作自动计算为候选，系统可展示“继续原计划”“局部调整”“重新比较方案”。用户可手动或按策略委托处理；所有自动变更有摘要与撤销。

### 3.5 每日/每周/长期回顾

日回顾不是强制打卡：展示计划时长 vs 实际、完成/未确认/未开始、被打断原因、明日容量和一个可执行建议。周回顾聚合真实偏差，提出估时范围或工作节奏假设，用户可接受、编辑、忽略。长期目标可拆里程碑→任务→工作单元，并显示目标路径受现实变化的影响；不是把 30 天视野误当长期目标边界。更正旧反馈会重算依赖的证据和未生效建议，不改写原始日志。

### 3.6 计划的三种操作模式（后续按验证逐步开放）

| 模式 | 适合用户/情境 | 系统权限与交互 |
| --- | --- | --- |
| 手动 | 想自己安排，或尚未建立信任 | 仅提示冲突和可选候选，手动编辑即生效/提交 |
| 辅助 | 大部分用户的默认起点 | 自动生成草案与差异摘要，用户一次确认整个影响集 |
| 委托 | 高频、低后果的局部调整 | 用户定义对象/时间/最大移动量/不可触碰项/通知方式，符合策略可自动提交；事后摘要和撤销窗口 |

委托不等于“模型写数据库”：模型提议操作，确定性工作流检查策略、当前版本与冲突，再提交。若用户授权自动调整，不强迫每次确认；影响超过本次授权范围、涉及他人权限或证据不足时升级为确认。完成/成绩这类现实事实不能仅由排程模型的主观判断推断，但可信外部证据和用户的特定授权可以开启更主动的记录路径。此处是事实可信边界，不是禁止主动规划。

### 3.7 扩展能力的完整链路（不再只列功能名）

| 场景 | 输入→处理→用户可见结果→修改/退出 | 关键异常 |
| --- | --- | --- |
| 重复任务 | 用户选择频率、结束条件、例外 → 规则生成独立实例 → 今日/计划呈现下一次 → 可只改本次或整个系列 | 休假/周次变化、某次已完成后修改系列；旧实例反馈不能被新模板覆盖 |
| 步骤与依赖 | 任务拆成工作单元并标先后/可并行 → 排程仅把已满足前置的单元视为可执行 → 详情显示被谁阻塞 → 可改依赖/跳过步骤 | 环形依赖必须可检测；用户仍能手动越过建议并看到风险 |
| 长期目标 | 设结果与期限/里程碑 → 形成近端工作单元和远端容量区间 → 今日只显示近期行动 → 回顾显示路径变化 → 可暂停/调整目标 | 未知工时不得编出半年逐日计划；目标改变不删除旧贡献记录 |
| 外部日历 | 按需授权只读/可写范围 → 拉取事件并标来源/新鲜度 → 影响本地容量形成差异 → 用户/策略处理 → 撤销连接后停用同步 | 重复事件 ID、权限撤销、外部改动覆盖手动锁定、时区漂移 |
| 协作与共享 | 创建共享范围及成员角色 → 对方提议或修改指定对象 → 本地显示作者和差异 → 允许合并/拒绝/撤销权限 | 个人计划细节不能因共享一个任务被全量暴露；冲突保留双方版本 |
| 导出/导入/恢复 | 选择范围 → 生成带版本、校验和、可读清单的文件 → 选择替换/合并及冲突处理 → 验证数量和计划版本 → 可安全退出 | 文件损坏、旧 schema、重复 ID、导入中断；原数据在完成验证前不能被清除 |
| Agent 委托 | 用户用具体示例授权对象+动作+期限+阈值 → 工作流监测触发并模拟变更 → 范围内提交/超界请示 → 展示记录和撤销 → 可随时暂停 | 多次触发造成循环、提议基于过期输入、模型建议引用不存在对象 |
| 智能提醒 | 确认/自动授权后的计划版本 → 派生期望提醒 → 系统调度/通知 → 打开对应对象并可调整偏好 | 无权限、电量延迟、旧版本残留、免打扰；不能用“未点击提醒”推断没执行 |

### 3.8 排程原则：从“按一个分数排”变为多目标、可解释的求解

当前固定 25/15/45/15 权重与 30 分钟/30 天常量可继续作为迁移期基线，但不应成为产品物理定律。目标规划器按以下顺序工作：

1. 建立输入快照：任务/步骤、实际剩余工作、可用窗口、承诺事项、目标、手动安排、策略和时区；每一项记录来源与时间。
2. 区分**不可违背的物理冲突**（同一人无法同时参加两个线下课程）、**用户承诺**（锁定、休息、共享约定）、**偏好**（上午学习、少切换）和**未知**（没有填写可用时间）。强度由用户/来源配置，用户可显式允许例外或并行，不能把所有课程/休息永久编码为一类硬约束。
3. 先做可行性：对截止前工作量与真实可用容量计算缺口；每项返回 `reasonCode`、受影响对象、最少需要补的时间和不可确定因素。可行性不等于全部能排下；部分计划也有价值，但不能隐藏剩余量。
4. 再做优化：候选方案分别权衡截止违约风险、承诺破坏、任务切换、休息保护、计划稳定性、用户重要性和目标进展。计划稳定性要惩罚无收益的挪动；无法从数据证明的“AI 适配度”不能压过用户明确意图。
5. 输出任务顺序、已排时段、待安排原因、容量风险、与当前计划的差异、关键假设。比较方案时展示事实与取舍，不给伪精确“全局最优分”。
6. 提交前再校验一次当前事实和策略；已经开始/完成的执行段不可被未来重排改写。用户手动排序优先，但可提示代价并允许按本人选择改动。

规划算法可先用确定性启发式逐步演进，测试以不变量（无非法重叠、范围不越权、同输入稳定）、典型难题集和真实用户取舍评价为准；不为“用了优化器/模型”本身加分。

## 4. 交互架构：移动端信息关系与页面规格

### 4.1 导航与跨页关系

手机保留四个高稳定入口，但重新定义为：**今日（行动）/ 收集与任务（对象）/ 计划（时间与取舍）/ 我（偏好与数据）**；“时间”若不能让用户预期里面也有计划，就改名“计划”。大屏改 Navigation Rail + 双栏，左侧任务/日期索引，右侧详情或计划；折叠屏按窗口大小而非设备名适配。所有跨页跳转保留返回路径、筛选与滚动锚点。Android 系统返回优先关闭弹层、再回上一级、再离开；确认提交中不吞返回，而是让操作快速结束或显示可恢复状态。预测式返回应展示目标层级而非跳错页面。

| 页面 | 首屏任务 | 主动作 | 次级入口/空态 |
| --- | --- | --- | --- |
| 今日 | “现在可做什么”+ 今日负载 + 待处理变化 | 开始/记录这一段 | 未建计划时展示清单和“一键规划/手动放置”；没有任务时快速录入 |
| 收集与任务 | 收集箱/活跃/待安排/逾期/已完成的少量快捷筛选 | 新建任务 | 搜索、详情、步骤与依赖、历史；避免复杂过滤器压首屏 |
| 计划 | 日/周时间轴 + 负载 + 候选方案 | 生成/编辑计划 | 时间约束、导入、冲突比较、版本；同屏看当前与候选的关系 |
| 我 | 提醒、自动化权限、数据与隐私、外观 | 管理偏好 | 证据、导入导出、账号同步（启用时）；不用一页滚完所有设置 |

### 4.2 页面级结构与关键细节

**今日**：顶部日期和可切换的“当前/未来日”；第一块仅一项主行动，标题、预计用时、来源/确认态与轻量原因。下面是容量条（可用/已排/已完成，不作“努力评分”）、时间轴摘要、待确认变更、待安排任务。当前计划和候选方案始终有固定标识；未来自动生效要标“已由规则处理，可撤销”。空日不鼓励填满，保留休息与空白。

**任务编辑**：快速输入区只需标题或描述；保存后展开时长范围、截止/开始窗口、预计周期、优先级、分类、步骤、依赖、重复、目标/附件。日期只代表截止或计划窗口，标签不能混用。编辑高级字段时实时显示“这会影响哪些安排”。字段错误贴近字段展示；离开未保存内容时提供保存草稿/放弃。Android 分享入口可直达收集项而非盲目建任务。

**计划页**：顶部模式切换（今天/本周/更远），中部时间轴展示固定承诺、可用窗口、计划工作单元和休息；底部待安排抽屉可拖入时间，但另提供“选择时段/移动到…”按钮。拖拽只改变候选或用户明确进入的编辑态；拖起保留手指抓取偏移，超出容器有阻尼，跨日需明确落点。行高按时间刻度，不用卡片高度代替时长。重叠时说明是现实冲突、计划冲突还是用户允许并行；不同原因给不同动作，不一律阻挡。轻量编辑在底部抽屉；复杂比较/长表单进全屏。小屏避免嵌套滚动 `AlertDialog`。

**方案比较**：最多 3 个有意义的方案并列摘要，列出“截止达成、休息保留、任务切换、未安排时间、受影响任务数”；点一个展开时间轴差异。用户可混合选择局部操作，但须重新校验整体结果。冲突页先给可理解的结论，例如“周三前缺 90 分钟”；再给可选操作，而非先显示算法分数。AI 理由是解释层，不应是计划唯一的证据。

**反馈与回顾**：工作段尾部弹出轻量反馈 sheet，可稍后处理；用户在通知中也可进入对应任务。状态按钮在任务和工作段层分离。每日回顾显示事实/未确认/推测三个区块，推测用“可能”语气。涉及取消、删除、共享影响的动作显示后果与撤销/确认。每条证据可追溯来源与更正入口。

### 4.3 交互状态和文案字典

| 状态 | 显示词 | 必须可做的下一步 |
| --- | --- | --- |
| 缺时长但已保存 | 待估时 | 补时长 / 只排顺序 |
| 未设置可用时间 | 暂无可用时间依据 | 添加窗口 / 先用任务清单 |
| 计划容量不足 | 时间不够（缺口 X 分钟） | 比较方案 / 手动调整 |
| 草案输入已变 | 方案需刷新 | 查看变化 / 保留编辑后重算 |
| 工作段结束未反馈 | 等待你的记录 | 完成这一段 / 部分完成 / 没做 / 稍后 |
| 自动化运行中 | 正在检查影响范围 | 查看进度 / 取消运行 |
| 自动调整已提交 | 已调整 N 项，可撤销 | 查看差异 / 撤销 / 暂停规则 |
| 服务失败但本地可用 | 智能建议暂不可用 | 用本地方案继续 / 重试建议 |

状态不只靠色彩、图标或动画表达。操作反馈包含成功、进行中、警告、错误，文案说明“发生了什么/会影响什么/下一步是什么”。

## 5. 前端视觉系统：安静、有呼吸的行动工具

### 5.1 审美命题与取舍

借鉴 Apple 应用的**内容先行、留白、字重层级、即时触感、动效可中断**，而非照搬 iOS 控件、大片玻璃或悬浮装饰。UI-UX Pro Max 的产品检索里“Productivity Tool → 清晰层级、Flat/Minimal、克制微交互”与本项目吻合；其自动生成的营销 Hero/Testimonials、网页 GSAP 滚动揭示、紫色 wellness 字体组合与 Android 生产力界面不吻合，因此舍弃。Repland 的气质是“计划像呼吸一样可调整”：密度随任务情境伸缩，严肃但不惩罚，留白表示可恢复空间而不是未充分利用。

视觉节奏为：**今日聚焦一件事 → 下方给足上下文 → 方案页展开权衡 → 编辑页容纳复杂度 → 回顾页回到克制的事实**。一个屏幕只保留一个强主按钮；同类次级动作采用一致的文本/图标处理。不是所有内容都做大卡片；列表承载高频扫描，卡片只用于计划摘要、风险、候选方案或明确分组。空状态有具体动作，不出现抽象插画挤掉用户任务。

### 5.2 设计令牌（建议值，需实机校对）

| 令牌组 | 浅色模式 | 深色模式 | 使用规则 |
| --- | --- | --- | --- |
| 背景 `surfaceBase` | `#F7F8F5` | `#101714` | 内容画布；比纯白柔和，但不降低阅读对比 |
| 主表面 `surfaceRaised` | `#FFFFFF` | `#19221E` | 有操作的卡片、sheet；叠层不超过两级 |
| 主文字 `textPrimary` | `#1F2A26` | `#E6EEE8` | 标题、任务名、时间；已测候选组合约 13.9:1 / 15.4:1 |
| 行动色 `action` | `#2F6B5A` | `#8BCAB1` | 主按钮、选中、链接；浅色在白上约 6.2:1，深色在深表面约 8.7:1 |
| 警示 `warning` | `#A66320` | 另行适配高亮琥珀 | 文案/图标配“需处理”，不得仅用色标风险 |
| 危险 `danger` | `#B3261E` | 单独校验 | 删除/不可行；必须带文字和范围说明 |
| 中性边界 | `#D9E2DB`（暂定） | `#39483F`（暂定） | 分割线与选中状态需做非文字对比测试 |

上述比值仅是指定前景/背景候选配对的计算，不等于整个界面已达无障碍标准。实际组件、状态层、禁用态、scrim、动态色与深色警示均须做自动对比检查与实机检查。系统动态色作为用户可选“跟随系统”方案；关键“当前/候选/冲突”语义不依赖动态色。图标同一套 Material 风格矢量，24dp 标准尺寸、视觉笔画一致；底栏不能再用文字首字当图标。中文默认使用系统无衬线字体，时间/数字可用系统等宽数字特性；不把英文 Lora/Raleway 强加到中文。标题 26–28sp、章节 20–22sp、任务名 16–18sp、正文 14–16sp、辅助文字最低 12–13sp 且对比充分，跟随用户字体缩放而不是固定高度裁剪。

布局以 4/8dp 基础刻度：手机水平边距 16–20dp，模块间 24–32dp，行内 8–12dp；平板内容最大阅读宽度约 720dp，双栏间 24dp。圆角依角色：任务行 8–12dp、信息容器 16dp、sheet 顶部 20–24dp；阴影只用于悬浮层，其他主要靠表面与间距区分。时间轴刻度和计划段边缘必须清楚，不使用泛玻璃背景承载小字。Android 系统栏与手势区采用 edge-to-edge 配合 Insets；固定底部动作给滚动内容预留真实底部空间。所有可点击区域至少 48×48dp，邻近目标需避免扩展触区重叠。

### 5.3 语义组件规范

| 组件 | 核心内容与操作 | 必需状态 |
| --- | --- | --- |
| `NextAction` | 任务名、当前时段/建议开始、预计用时、一句缘由、主操作 | 可开始、进行中、已过时、无可行动作 |
| `TaskRow` | 标题、期限、剩余工作、动态排序理由的简述 | 待安排、逾期、进行中、已完成、锁定/关联目标 |
| `TimeBlock` | 起止、来源、工作/课程/休息、可拖动边界 | 当前、候选、冲突、固定、委托变更 |
| `PlanDelta` | 旧→新、影响数量、原因、取舍 | 待确认、可自动处理、已提交可撤销、过期 |
| `CapacityMeter` | 可用/已承诺/已完成与缺口，单位一致 | 已知、部分未知、超载、无输入 |
| `FeedbackSheet` | 这一段的反馈，再补任务级状态 | 未记录、已保存、可更正、后续建议 |
| `PolicyScopeChip` | 代理能动哪些对象、多大范围、何时失效 | 启用、暂停、待批准、超界 |

组件状态由 `UiState` 类型化映射，不能在 Composable 中靠 `null` 和字符串组合猜状态。每个状态有 TalkBack 宣读、焦点顺序、禁用语义、键盘/外接输入替代；拖放均有菜单动作。图标旁已有文字时将装饰图标从无障碍树隐藏；独立图标按钮提供本地化名称和选中/展开状态。保持系统字体放大到最大、深色模式、横屏和窄屏都可操作。

## 6. 动效与触感：让变化可理解，而非不断表演

依 Emil Kowalski 的决策顺序逐项问：是否需要动、为何动、如何进入/退出、是否可中断、速度是否匹配频率。借 Apple 的物理连续性和当前可见值接续原则，但在 Android 上用 Compose/系统手势原生实现，不能把 Web CSS 或 GSAP 作为技术方案。任何动画不得延迟任务保存、计划确认或返回。频繁动作（任务行切换、键盘录入、重复查看今日）原则上仅即时状态反馈；有空间关系的低频变化才使用位移/弹簧。

| 场景 | 目的/频率 | 规格草案 | Compose 实现与退出 |
| --- | --- | --- | --- |
| 按压任务行/按钮 | 即时确认，高频 | 触下原生 ripple/状态层即刻出现；若缩放，0.98–0.99、100–140ms，不移动相邻布局 | `interactionSource` + `indication`；触离/取消即时复位，不能依赖点击完成才反馈 |
| 今日任务状态变化 | 让完成/部分完成关系明确，中频 | 图标/文本过渡 120–180ms；原位置更新，不整页飞入 | `AnimatedContent` 仅包状态局部；快速连续更改从当前值重定向 |
| 草案差异展开/收起 | 解释信息层级，偶尔 | 透明度 + 小范围纵向位移 160–220ms；退出 120–160ms | `AnimatedVisibility`，内容尺寸复杂时先测重排和帧耗 |
| 计划段拖放/移动 | 保持手与内容 1:1，偶尔 | 拖动与手指同步；释放到有效位置用临界阻尼弹簧，无夸张反弹；冲突区域直接反馈 | `pointerInput`/拖放 API + `Animatable`；接管当前显示位置和速度；系统返回/取消能中断 |
| 底部反馈 sheet | 告诉用户从何处进入，偶尔 | 进入约 220–280ms，退出更快 160–220ms；背景微弱压暗而非全屏模糊 | Material3 sheet；优先平台默认行为，返回和向下拖动同一路径退出 |
| 方案切换 | 保留空间参照，偶尔 | 不做整屏横飞；摘要即时更新，时间轴受影响段 180–240ms 移动/淡化 | 有 stable key 的局部 `animateItem`/`Animatable`；输入多次时取消旧目标 |
| 提交成功与撤销 | 明示版本已改变，较少 | 轻量状态条从当前层出现 160–200ms；必要时一次轻触感 | Snackbar + 版本号/撤销动作；不能用彩纸或持续脉冲代替可信度 |

动效令牌建议 `instant=0`、`fast=120ms`、`standard=180ms`、`spatial=240ms`、`spring=criticallyDamped`；不是强迫每个场景使用同一时长。沉入/消失尽量比进入快；默认无弹跳，仅真实拖拽释放允许极弱过冲。系统设置减少动画时，位移改短淡入或直接状态切换；关闭系统动画时尊重系统比例。触感只用于拖动拾取/落点、重要确认、明显错误，遵守系统触感设置，不对每个勾选震动。通知声音由系统渠道和用户设置管理。性能验收以真实中低端设备的帧耗/掉帧和触摸响应为准；大列表不做逐项瀑布式入场。

**明确拒绝的动画**：首页不断“呼吸”的 CTA、每天第一次打开所有任务逐一出现、任务完成彩纸、因每次排序微调导致整列表跳动、玻璃模糊覆盖多层小字。这些或让高频操作变慢，或把“计划变了”伪装成娱乐反馈。这里的“呼吸”是留白与节奏，不是循环动效。

## 7. 前端工程设计：页面不是业务流程控制器

### 7.1 分层与模块

```text
app-shell/
  ReplandApp / Navigation / WindowSize / PermissionCoordinator
feature-capture/ feature-tasks/ feature-today/ feature-plan/
feature-time/ feature-review/ feature-settings/ feature-automation/
designsystem/
  ThemeTokens / Type / Icons / Components / Motion / Accessibility
application/
  usecases-or-workflows / commands / results / authorization / queries
domain/
  task / time / planning / execution / policy / evidence
adapters/
  room / pdf / reminders / system-calendar / export / ai-gateway / sync
```

先从 4100 行左右的 `ReplandApp.kt` 提取导航壳与三个最复杂流程（创建任务、生成草案、提交/反馈），不为每个小点击创建“Workflow”类。屏幕只发送 `UserIntent`，ViewModel 映射单一 `UiState`（Loading/Ready/Empty/Problem/Recovering）；跨页面逻辑在 application 用例中实现。规划输入由用例从 Repository 一致读取，避免 UI 挑选任务、时间块和锁定段时漏项。Composable 无数据库/网络写能力；预览数据和真实数据共用同一组件。列表使用 stable keys、惰性布局；昂贵 PDF 解析、排程与差异计算离开主线程。保存操作显示确定的结果与重试，不能 `runCatching` 后静默吞错。

### 7.2 平台优势，不复制 iOS

- **Android 通知与快捷操作**：从计划通知直达对应工作段；可提供“稍后提醒/打开反馈”，但不能把误触通知动作当现实完成。通知权限按上下文请求，拒绝后仍在应用内显示提醒计划与设置入口。
- **Widget / App Shortcuts / 分享入口**：今日下一步、一键收集、最近任务；Widget 仅展示当前已生效计划与近期时间，不把过期草案当事实。数据读取有限制且需轻量；交互落到明确目的地。
- **适配设备**：手机底部导航，大屏导航轨/双栏，折叠屏尊重铰链与窗口 Insets；外接键盘有创建、搜索、上/下移动备选，鼠标悬停只是增强。
- **系统体验**：edge-to-edge、预测式返回、系统深色/动态色（可选）、TalkBack、系统字体缩放、震动偏好；没有 iOS 导航栏和玻璃层的生搬硬套。
- **离线可用**：Room 是本地操作基座；联网建议与同步是附加能力。即使以后服务端上线，进入今日、手动编辑和本地反馈也不能被请求阻塞。

### 7.3 页面状态与导航契约

路由至少能表达 `task/{id}`、`plan/day/{date}`、`proposal/{id}`、`plan/version/{id}`、`feedback/{sessionId}`、`policy/{id}`；深链目标不存在时给可恢复提示。`SavedStateHandle` 保留筛选/未提交表单的轻状态，跨进程长时草案落 Room。导航背栈不存领域事实；返回草案时重新读取版本与输入签名。Plan 页面支持从今日跳到某一时间段并返回同一滚动位置。键盘出现/消失时固定 CTA 不遮挡输入；sheet 和全屏编辑明确谁拥有返回动作。自动化执行 UI 的取消动作必须取消后续工具调用/提交，已提交部分明确显示并可撤销，不能假装“取消了整个事实”。

## 8. 本地“后端”与数据一致性：先把非 Agent 链路做成可靠系统

### 8.1 事务边界与状态机

**任务**：`Captured → Active → InProgress ↔ Paused/Deferred → Completed/Cancelled/Replaced`；恢复是新事件而非删除旧结果。工作段状态与任务状态分离。自动计时能证明应用计时器运行，不能证明学习成果；成果与最终完成须来自用户反馈或有出处的外部证据。未来策略可允许基于特定可信证据的自动状态记录，但要保存证据关联、可撤销，不能虚构不可观测事实。

**方案**：`Building → Ready → Edited → Stale/NeedsDecision → Applied/Discarded/Failed`。方案携带 `basePlanVersionId`、`inputRevisionHash`、`triggerReason[]`、`operations[]`、`affectedIds[]`、`policyDecision`、`createdAt/expiry`。编辑每一步可撤销/重做。提交前重新验证快照、对象仍存在、授权、容量、重叠及用户偏好；版本不同则做三方差异并让用户选择刷新/保留可合并编辑，不能“最后写入者赢”。手动即时编辑可以视作用户发出的 `ApplyPlanOperations`，内部仍先验证再提交，不需要强迫显式草案页。

**计划版本**：提交生成新 ID，旧版本和引用关系不改。`setSegmentLocked` 这类当前直接修改段的操作，应改为新计划修订或记录附加的锁定决策，再由查询构建当前状态；这样历史版本不会被后来动作污染。计划恢复创建新版本，恢复安排和排序但不抹去恢复点之后真实发生的反馈；若历史安排与现在已完成任务冲突，先列差异让用户处理。自动化提交也遵循相同版本机制，作者字段记录具体策略 ID。

### 8.2 提议的数据表与迁移策略

现有 `tasks`、`execution_logs`、时间约束表、`plans`/`plan_segments`/`plan_task_order`、提醒设置和证据表继续使用。按功能落地逐步增加：

| 新表/字段组 | 最小用途 | 不宜过早做的事 |
| --- | --- | --- |
| `captures` | 保留原始输入、来源及转化关系 | 不把所有原文永久上传 |
| `plan_proposals` + `proposal_operations` | 草案持久化、差异、来源和过期 | 不把每次 UI 展开都持久化 |
| `workflow_runs` + `decisions` | 跨步恢复、幂等、自动化审计 | 不为单一标题编辑创建流程实例 |
| `plan_revisions`/计划元数据 | 父版本、输入签名、作者、提交原因 | 不为“完整事件溯源”先迁移全部表 |
| `work_units` + `commitments` | 支持步骤、依赖、外部事件与任务区分 | 不把课程与任务永久绑定为同一行 |
| `policies` + `policy_executions` | 具体可委托动作、阈值、撤销/暂停 | 不保存无限期全局“Agent 可代我做事” |
| `reminder_desired_state` | 对账目标提醒及投递键 | 不依赖 UI 调用顺序保证通知一致 |
| `external_links`/`sync_outbox` | 可选集成/同步的源 ID、修订与待上传变更 | 未验证跨设备前不强迫用户建账号 |

每次 Room migration 写明旧值→新值映射、默认值、回滚/灾难恢复策略与真实升级设备测试。`estimatedDays` 从必填迁为可空时，既有 1 天保持原数据，新录入缺失表示 unknown，不能用 1 天冒充用户预期。任务标题/描述任选一项的校验需同步修改 Room、ViewModel、错误文案和仪器测试。导出 JSON 升级为带 `schemaVersion` 的可复原快照并提供导入预览与去重/合并；在真正实现验证前，不宣称“可导出=可恢复”。

### 8.3 计划提交、提醒与时间

`ConfirmPlan` 在 Room 事务中写新版本、当前指针、决策关联及**期望提醒状态**；事务成功后异步协调器把设备实际提醒与期望状态对账，失败可重试，不因 AlarmManager 写失败回滚已确认计划。旧版本提醒取消、新版本提醒创建使用稳定派生 ID 和幂等键；启动、重启、时区/时间调整、权限改变后再对账。提醒“准时”不得作严格保证：Android 的非精确闹钟可能延迟，确需精确的场景要另行确认权限/电量代价和平台限制。时间存储区分 `Instant`、本地日历日期、用户时区与浮动本地时段；跨 DST、旅行、学期周次变化需要明确重算，已执行历史不重写。当前 30 分钟量化可作排程默认，不应限制 15 分钟碎片任务、长课程或跨日目标的表达；显示粒度与计算粒度可分离。

### 8.4 非 Agent 用例接口与结果契约

```kotlin
sealed interface PlanCommand {
  data class Generate(val reason: Set<Trigger>, val scope: Scope) : PlanCommand
  data class Apply(val proposalId: Id, val expectedVersion: Id, val decision: Decision) : PlanCommand
  data class ManualEdit(val operations: List<PlanOperation>, val expectedVersion: Id) : PlanCommand
  data class Restore(val versionId: Id, val expectedVersion: Id) : PlanCommand
}

data class WorkflowResult(
  val status: Status,            // APPLIED / NEEDS_DECISION / STALE / FAILED
  val planVersionId: Id?,
  val proposalId: Id?,
  val changedIds: Set<Id>,
  val warnings: List<StructuredWarning>,
  val recoveryActions: List<RecoveryAction>
)
```

这是示意契约，不是现有可编译代码。`CaptureTask`、`ImportTimetable`、`GenerateProposal`、`ApplyPlan`、`RecordFeedback`、`ReconcileReminders`、`ReviewDay`、`RestoreVersion` 分别有输入、状态、幂等键、失败恢复。所有入口（任务编辑、时间变化、反馈、外部日历）发布同一种结构化 Trigger，统一去重/局部影响计算；UI 不重新拼 Domain 输入。方案生成应确定性可重放：相同快照和规则版本产生相同排序/容量解释，随机/模型因素只作为单独的可审查候选层。高频编辑可合并触发，但不会丢掉最后一次更新；后台计算完成时若版本已旧则废弃结果并重新生成，不能覆盖用户刚拖动的安排。

## 9. 后续服务端与可选同步：为能力扩张预留，不抢走本地基座

### 9.1 架构分期与职责

| 层 | 阶段一：不依赖网络 | 阶段二：智能网关 | 阶段三：可选同步/集成 |
| --- | --- | --- | --- |
| Android | Room 主数据、规划器、流程与提醒 | 请求预览、最小化数据、校验建议 | 本地写入优先、同步队列与冲突 UI |
| 服务端 | 无 | 鉴权、限流、模型编排、预算、响应结构化、短期运营审计 | 账号、隔离存储、同步游标、外部连接器、恢复机制 |
| 外部来源 | PDF/手填 | 模型供应商 | 日历/课程/文件源（逐一授权） |

正式联网版需有意调整当前 APK 的 `INTERNET` 构建防线，按 build variant 与功能开关审计，不能偷偷加入网络权限。开发个人 BYOK 是另一条隔离实验路径，不是正式网关架构的捷径。阶段三不把同步写作必然：先验证用户是否真的在多设备损失计划，及其愿意承担的隐私/维护成本。

### 9.2 API 与服务端能力规格（拟议）

智能网关可采用 `/v1/advice/task-parse`、`/v1/advice/plan-options`、`/v1/advice/review` 三类类型化端点，统一请求含 `contractVersion`、`requestId`、`purpose`、`scope`、`inputRevisionHash`、`consentReceipt`、`minimalContext`；响应含 `proposalId`、`modelVersion`、`structuredOperations`、`rationale`、`assumptions`、`uncertainty`、`expiresAt`，绝不返回“直接执行的 SQL/任意命令”。HTTP 请求需要短时授权、幂等键、大小与超时上限；服务端核验用户/设备身份、配额、成本、模型故障与提示注入边界。日志默认只留请求类型、结果码、耗时、成本和匿名化诊断，不留原任务全文；留存期、区域、删除时限须产品评审后明确。内容输出在客户端再检查引用对象、时间、约束、作用域和新鲜度。

同步若启用，资源 API 需覆盖任务/事件/工作单元/计划修订/执行日志/策略/证据，并以稳定 ID、`revision`、删除墓碑、游标、批量上传和冲突响应为基础。客户端 outbox 对 `operationId` 幂等重试；计划与执行日志保留两侧历史，不做静默覆盖。共享计划和协作需要单独的成员角色、可见范围、撤销、消息/通知、对方改动预览；个人 Agent 授权不能自动成为团队写权限。外部日历连接器必须保存源事件 ID 与权威性/刷新时间，外部撤销后停止拉取并说明本地副本处理。

### 9.3 安全、隐私与可用性不是“旧限制”

真正不可妥协的是系统不能谎称知道现实、不能泄露他人数据、不能把密钥放 APK、不能在故障时丢任务。其他应做**可配置策略**：允许用户对低风险重排选择自动处理，允许导入更多数据，允许 Agent 参与多步工作；前提是授予可见、可撤销、有期限的权限。先建威胁模型：模型诱导跨任务修改、恶意 PDF/日历内容、共享对象越权、同步冲突覆盖、误触大规模清除、自动化循环和推送骚扰。限权、输出 schema、资源引用校验、影响集审核、速率与成本上限、事后审计是让能力跑得更满的条件，不是拒绝能力的理由。

## 10. Agent 与 Workflow 的创新根基：把“协作”做成产品，而非聊天外挂

### 10.1 权限阶梯与工具设计

传统应用反复让用户在字段、时间、反馈、冲突页搬运上下文；确定性 Workflow 首先把这些步骤连起来。Agent 之后接入相同的读取/提议接口。可提供四级：`Observe`（解释）、`Draft`（写候选）、`ScopedApply`（在策略内执行）、`Escalate`（超界请求确认）。工具按能力拆分为 `readAffectedContext`、`proposeTaskFields`、`simulatePlanOperations`、`compareOptions`、`submitAuthorizedOperations`、`explainRevision`，不提供“一把万能写入”工具。`submitAuthorizedOperations` 是工作流工具，它复核 policy 与当前版本，不是模型直写数据库。

每次代理运行有 `runId`、触发源、用户/策略授权、读取数据摘要、工具调用与版本、提议、被拒原因、实际提交差异、撤销入口。对自动化设静默预算（例如一天最多 N 次局部调整）、抖动合并窗口、重复变化检测、暂停与紧急停止。系统可说“我已为你重排两项，未碰你锁定的学习时段”，点开看明细；高风险或无法解释时必须停下来请用户裁决。Agent 不需要总是聊天，可在任务录入、冲突面板、每日回顾中以内嵌建议出现；可选自然语言总入口用于高级用户，但它仍走相同授权和工具链。

### 10.2 三个可验证的创新体验

1. **零摩擦任务理解器**：自然语言/分享/语音进入 Capture；系统只问一个最关键的不确定项，再产出可编辑任务与步骤。指标是“从想到到可执行”的时间和字段修正率，而不是解析字数。
2. **现实变化协商器**：新课/任务/延期来了，系统同时给“维持承诺”“减轻负载”“最快交付”选项，显示代价与受影响范围。低后果时按用户策略自动调整；高后果时只问一次有意义的问题。指标是冲突解决时间、意外移动率和撤销率。
3. **执行校准器**：从实际时长、部分完成与中断证据提出可编辑的估时区间/拆分方案；不是对用户下结论。指标是下次预测误差、用户感到计划可信的程度、建议采纳后的反悔率。

### 10.3 不走路径依赖的技术选择复审

| 待决策问题 | 看似自然的旧路 | 本方案备选及采用条件 |
| --- | --- | --- |
| 每次变更都要确认？ | 全部草案手动确认 | 提供手动/辅助/委托；以用户撤销率与误伤率决定默认阈值 |
| 一定要一张时间轴？ | 今日全屏时间线 | 用户只有零碎任务时以行动队列为主；高承诺密度时切时间轴，做原型测试 |
| 所有数据都留本地？ | 永不建后端 | 本地为快路径；跨端/协作/模型收益达到门槛时引入同步与网关 |
| AI 只能建议？ | 永久只读 | 允许受策略约束的工具执行；越权、不可逆、不可观测事实不自动提交 |
| 计划必须 30 分钟/30 天？ | 以现有算法常量当产品规则 | 近期以半小时视图、长期多尺度；粒度受任务特征和用户选择驱动 |
| 需要事件溯源？ | 一次性重写全部存储 | 先计划版本+追加反馈+决策关联；只有查询/审计无法满足时再评估事件溯源 |
| 是否先做“全能 Agent”？ | 一个对话框解决所有事 | 先场景内工具；当用户确实需要跨情境发起时再加入统一入口 |

## 11. 实施路线：完整方案分层交付，不缩减目标体验

| 阶段 | 实施内容 | 退出条件 |
| --- | --- | --- |
| A. 可信本地底座 | 修正最小任务校验；页面信息层级与设计令牌；持久草案、过期检测、错误状态；本地规划与反馈重构为显式用例；版本与提醒对账 | 首次使用→安排→执行→反馈→重排→恢复端到端通过；进程被杀/断网/重启后不丢用户输入；当前计划与草案不会混淆 |
| B. 计划能力拓宽 | 工作单元/步骤、依赖、重复规则、容量情景比较、可配置规划视野与粒度、轻量周回顾；Android Widget/Share/Shortcuts | 真实用户在课程密集周能处理新任务和冲突；方案解释与手动操作一致；大字/深色/横屏/无障碍可用 |
| C. 受控智能与委托 | 网关、结构化建议、Agent 工具、策略中心、自动化审计/撤销、成本与隐私控制 | 关闭 AI 时闭环同样成立；越权输出无法提交；自动调整有低误伤与可接受撤销率 |
| D. 连接与跨端 | 外部日历、可选账号同步/恢复、协作试验、长期目标 | 双端离线冲突可见可处理；数据删除/迁出可信；协作权限不被个人策略继承 |

阶段是依赖顺序，不是功能排除表。若用户测试发现重复任务或外部日历比某个阶段 A 的 polish 更直接影响闭环，应调整顺序，但不得跳过一致性与迁移质量。阶段 A 不是低配版：它必须把“完整非 Agent 闭环”做完；后续能力从同一接口接入。

### 11.1 可执行验收矩阵

| 场景 | 关键断言 | 测试层 |
| --- | --- | --- |
| 仅一句描述创建任务 | 原文不丢、可保存、待安排明确、无伪造时段 | 单元 + UI |
| 有课程/休息/锁定时规划 | 不侵占来源标记为禁止的窗口；容量不足有分钟数与原因 | Domain property + 仪器 |
| 草案编辑中杀进程/改任务 | 可恢复编辑；提交时检测输入变化，不覆盖新事实 | Room migration + UI |
| 连续快速拖动再返回 | 无旧动画跳变；最终位置与版本一致；手势/返回不冲突 | 真实设备 UI/性能 |
| 部分完成再恢复历史计划 | 原反馈仍在；剩余工作合理；恢复生成新版本 | 集成 |
| 提醒权限拒绝/重启/时区变更 | 不错误承诺准时；设备提醒与当前计划对账 | 仪器/手动设备 |
| AI 超时/注入/跨范围操作 | 本地方案可继续，越权提交被拒，有可读原因 | 契约/安全 |
| 自动化循环/重复同步 | 幂等、速率上限、可暂停和撤销 | 集成/故障注入 |
| 大字、TalkBack、深色、折叠 | 48dp 触区、焦点顺序、非颜色状态、无遮挡 | 无障碍/视觉回归 |

质量度量同时看任务：首个可用计划用时、今日找下一步耗时、冲突解决耗时、草案放弃原因、意外修改/撤销率、估时误差、7 日回访；及系统：崩溃、丢草案、版本冲突、提醒错发、掉帧、网关错误与成本。当前无分析 SDK，内测可先采用用户自愿访谈与本地诊断导出；上线采集前必须有告知与最小化设计。

- [Android Compose 无障碍与最小触控目标](https://developer.android.com/develop/ui/compose/accessibility/api-defaults)：原生组件语义与 48dp。

- [Android 自适应导航](https://developer.android.com/develop/adaptive-apps/guides/build-adaptive-navigation)：窗口大小驱动导航结构。
- [Android 预测式返回](https://developer.android.com/develop/ui/compose/system/predictive-back)：返回层级和过渡。
- [Android 通知运行时权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)：按情境授权。
- [Android Alarm 调度](https://developer.android.com/develop/background-work/services/alarms)：本地提醒时效限制。
- [Apple Human Interface Guidelines — Motion](https://developer.apple.com/design/human-interface-guidelines/motion)：借鉴设计原则，不移植平台控件。

## 13. 对抗性审查（最终关口）

| 攻击/质疑 | 本方案可能失败的地方 | 必须通过的反证或修正 |
| --- | --- | --- |
| “能力优先”会变成无限需求池 | 每一域都可扩张，研发分散 | 每阶段只选最能缩短用户闭环的垂直切片；退出条件必须实测，不以页面数量证明进展 |
| 委托权限会重演不可控 Agent | 策略界面太复杂，用户不理解作用范围 | 默认小范围、具体例子预览、自动运行日志和一键停用；用越权测试与用户理解测试校验；否则只开放辅助模式 |
| 过度审慎会让用户每次点确认 | 旧边界仍潜入交互细节 | 统计每周确认次数与撤销率；高频低后果动作默认直接操作/批量授权；只有高后果升级确认 |
| 过度自动化会伤害信任 | 系统把学习成果或完成状态当可推断事实 | 明确“观测到计时/计划到点”≠“任务完成”；用户可更正；Agent 无法直接伪造结果 |
| 任务模型太庞大会延缓 A 阶段 | 工作单元/承诺/目标一次建齐会重写所有 DAO | 先接口语义和迁移路径，再逐能力落表；旧简单任务零强制字段，增量升级 |
| “安静审美”会掩盖风险 | 低饱和界面看不出超载与冲突 | 风险文案、位置、图标和容量数字同时表达；对比检查，真实任务测试 3 秒内能定位冲突 |
| Apple 借鉴压过 Android 原生 | 玻璃、弹性/手势与 Android 返回或性能冲突 | 使用 Material3/Compose 与系统手势；仅采纳可解释的层级/触感原则；低端设备和 TalkBack 通过才保留动效 |
| “完全离线”与“联网智能”撕裂 | 后端一上线，核心体验开始等待请求 | 核心写入和计划展示本地先行；远程建议是并行候选；离线/超时路径与联网路径共用事务规则 |
| 历史恢复让现实倒流 | 回退快照含早已完成或取消的工作 | 只恢复计划意图的可合并部分；执行事实追加不删，冲突必须可见 |
| 规划算法看似精确却不可靠 | 30 分钟格子和单一估时给虚假确定性 | 时长范围、容量缺口、未定项与多方案并呈；检查预测误差，不把“排满”当成功 |
| 竞品调研不是用户研究 | 模仿功能矩阵会错过真正痛点 | 用大学新生真实一周情境、访谈和原型测试校准入口、确认频率和计划粒度 |

**最终未决项**：目标用户是否首先需要“替我排”还是“帮我敢于开始”；计划编辑应默认即时生效还是候选预览；可委托的低后果阈值如何定义；外部日历、重复任务、长期目标何者最早进入；同期任务并行如何解释；跨端需求是否足以支付服务端复杂度。这些不应被旧文档预先判死，也不能靠本报告臆断。下一步以可操作原型与真实用户任务测试给出证据，再更新正式产品术语和 ADR。
