# Repland 前端改造提示词

使用方法：复制下方“提示词正文”的全部内容，发给负责新项目的开发助手。开头的项目资料可按需填写；未填写的内容由助手先从项目中查找。建议同时提供旧版的首页、总计、详细、我的页面截图，以及运行录屏。

设计基线：本地 2026-10-15 交付的 Repland 设计副本，已于 2026-10-17 核对页面、主题和动效源码。本提示词不预设下一版的后端功能。

## 提示词正文

你是一名熟悉产品设计、交互设计和客户端开发的工程师。请直接在当前项目中完成 Repland 的前端改造，让新的功能与后端接口使用起来完整、自然，并延续我已经认可的 Repland 设计副本的视觉与运行体验。

我的目标包括静态布局、点击反馈、页面过渡、表单操作、数据更新和异常处理。请完成实际实现、运行验证和交付，不要只给设计建议或静态效果图。

### 一、项目资料与处理原则

- 项目位置：【未填写时使用当前工作目录】
- 新功能需求：【填写需求，或读取项目中的需求文档】
- 后端接口与数据模型：【填写文档位置，或读取已有接口定义、客户端与模型】
- 旧版参考资料：【可附截图、录屏、设计副本源码；没有资料时按下文设计规范实现】
- 本次重点与特殊限制：【按需填写】

先读取项目规则、README、页面入口、技术栈、主题组件、状态管理和接口契约，梳理现有功能及本轮变化。业务范围、权限、字段、优先级、状态和时间含义以新需求及新后端契约为准；旧版作为视觉与交互基线。

旧参考版本采用 Kotlin、Jetpack Compose 和 Material 3。如果新项目仍使用这一技术栈，优先复用原生组件与现有架构；如果已经换成其他技术栈，使用新项目的技术栈实现相同体验，不为复刻界面额外更换框架。

先简短列出页面调整、接口映射和设计方案，再继续实现。普通布局与实现选择自行判断；仅对无法从项目中确定、会改变业务含义的缺口提出具体问题，同时推进不依赖该答案的工作。

### 二、整体视觉：清爽、柔和、多色、层次清楚

延续当前副本的浅色纸面、白色大圆角卡片、清晰日期、时间侧栏和柔和多色强调。界面的重点应是用户的日程、任务和下一步操作。

将以下颜色集中为主题变量或设计令牌，避免在各页面分散硬编码：

| 用途 | 浅色基准 |
| --- | --- |
| 页面背景 | #F7F8FC |
| 卡片背景 | #FFFFFF |
| 主要文字 | #242831 |
| 次要文字 | #606572 |
| 主要行动色 | #326B75 |
| 浅蓝 | #EAF2FF |
| 薄荷绿 | #EAF7EF |
| 浅紫 | #F2EDFF |
| 米黄 | #FFF5DC |
| 淡粉 | #FFEFF3 |

使用多种柔和亮色，让不同入口、事项和选中状态有变化。日程入口以浅蓝为主，任务以薄荷为主，助手以浅紫为主，我的以淡粉为主；新功能从同一色板扩展。主操作保持足够清晰的强调色，成功、警告、错误仍使用明确的语义色。

事项颜色可以呈现随机分配的丰富感，但必须通过稳定 ID 或持久化映射确定。同一事项在总计、详细、详情及重新打开后保持同色；刷新、排序、切页和动画不得使颜色反复变化。颜色不独自承担优先级或状态含义。

渐变只用于新增日程入口、个人资料等少数重点区域，保持轻浅。阴影、描边和分隔线用于表达层次。避免整页高饱和色块、过多装饰、重阴影和无意义的统计卡片。

为深色模式定义对应的深色表面与文字，参考背景 #171921；不要直接将浅色卡片贴到深色背景上。正文与次要文字均检查实际背景下的可读性，普通文字对比度至少 4.5:1。

### 三、排版、尺寸与页面组织

采用中文友好的系统无衬线字体，时间数字对齐。正文以 14–16sp 为基准，分组标题约 20sp，页面日期约 28–32sp，按实际设备调整；网页采用对应的可缩放单位。

主要内容左对齐。手机左右边距约 20dp，主要卡片圆角约 24dp，卡片内部留白约 16–20dp，组间距约 16–24dp；使用统一的 4/8dp 间距体系。按钮、输入框和标签使用有层级的圆角，不把所有组件做成同一种形状。Android 点击区域至少 48dp，并遵循目标平台的无障碍要求。

旧版主要导航为“日程、任务、助手、我的”，时间设置位于相应设置入口。根据新功能合理调整信息架构，维持常用操作的位置稳定；底部主导航控制在 3–5 项，更多功能放入相关页面。

新建的详情页、设置页、弹窗和抽屉必须共用同一套字体、色彩、图标与反馈规范。使用统一的矢量图标系列，图标按钮提供可读名称。处理状态栏、手势区、软键盘和底部导航的遮挡。

### 四、日程首页与“总计／详细”

首页延续“日期 → 新增日程入口 → 日/周/月 → 总计/详细 → 日程列表”的主要结构，按新项目功能调整。新增入口采用轻浅渐变、大圆角、清楚的加号和真实的新增操作。空状态提供简短说明和可执行入口。

保留原合轨、分轨的使用目的，界面名称使用“总计”和“详细”。这是同一份日程数据的两种展示方式，切换视图不得修改任务优先级、实际起止时间、轨道归属或计划。

“总计”的要求：

- 根据事项的真实起止时间拆分重叠区间，同一时段的事项在一行从高优先级到低优先级排列。
- 例如 A 为 09:00–10:00、B 为 09:30–10:30，应展示 09:00–09:30 的 A、09:30–10:00 的 A 与 B、10:00–10:30 的 B。
- 高优先级视觉更突出，后续事项通过底色、强调线等逐步减弱。保持文字清晰，不对整张卡片和正文一起降低透明度。
- 窄屏在事项行内部支持横向查看，并让用户能发现后续内容；页面主体不产生意外横向溢出。
- 点击任何时间片中的事项，都打开对应的原始事项。

“详细”的要求：

- 按新后端的真实优先级从高到低分组或排列；组内按实际开始时间稳定排序，同值使用稳定标识消除跳动。
- 显示完整的事项名称、起止时间、优先级及必要备注，允许打开详情与相关操作。
- 未设置优先级的事项放在最后，并明确标注。课程、休息和固定安排单独标识，不伪造任务优先级。

旧版优先级文字为“必须、高、中、低、未设置”；新后端如有变化，集中映射，不沿用已失效的枚举或评分规则。

保留新项目仍支持的任务查看、时间编辑、备注、执行、移除安排及轨道设置等入口。已完成、已取消和时间已结束按真实含义展示，支持适当折叠；仅仅经过结束时间不能由前端擅自判定任务完成。

### 五、“我的”页面与个人资料

“我的”最上方放置个人资料卡：约 80dp 的圆形头像、用户名、清晰的“更换头像”和“编辑用户名”入口。延续淡粉与浅紫的轻浅背景，主要卡片圆角约 24dp。窄屏、大字体下操作可换行。

头像支持系统图片选择器、更换、取消和恢复默认。加载或保存失败保留原头像并显示可理解的反馈。控制解码与缓存尺寸，参考旧版最长边 384px 的本地展示副本；新后端有上传规格时按契约处理，避免把原始大图直接用于列表或长期放在内存中。

用户名支持编辑、保存、取消、输入校验和失败重试。旧版默认“Repland 用户”，去掉首尾空白，允许 1–24 个 Unicode 码点，拒绝换行和控制字符；新契约有不同规则时按新规则校验。

旧版资料为本地保存。如果新项目提供账号和同步能力，正确接入服务端资料、上传与保存状态；如果仍为本地模式，切页、重启和覆盖更新后保持资料。明确存储方式，不能让本地保存看起来像已经同步到云端。

### 六、运行时动效：让每次操作都有清楚反馈

将动效做成统一、可复用的能力，覆盖按钮、筛选、导航、日程项、展开分组、弹窗、抽屉及资料更新。动效解释操作产生的变化，并保持界面可以立即使用。

参考旧版的节奏作为起点，按目标平台和交互距离调整：

- 按下反馈约 90ms，普通按钮缩至约 96.5%，日程项约 97.5%，主加号约 93%；缩放只改变视觉，不缩小点击区域或挤动周围布局。
- 松开后轻弹恢复，保留原生涟漪、键盘焦点及禁用语义。点击动作立即执行，不等动画完成再请求或保存。
- 页面切换约 240ms，使用短距离移动与淡入；底部导航稳定，不让每张卡片依次飞入。
- 展开约 260ms、收起约 180ms，内容尺寸平滑变化，箭头随状态旋转。连续点击能及时反向，不排队播放。
- 表单分步前进与返回有一致方向；图片替换采用短暂淡入，数据更新只对实际变化的局部反馈。

快速连续切页、重复开关弹窗、切换总计与详细时，取消或更新过时过渡。退出内容不得继续接受点击或重复触发请求。保证同一业务动作不会因为动画或重组而重复执行。

尊重系统关闭动画或减少动态效果设置，关闭时直接呈现最终状态。动效不得成为保存成功的判断条件；页面停留时避免循环装饰、持续闪烁和无业务用途的后台刷新。

### 七、随新后端一起完善真实功能与状态

先建立“页面/组件 → 用户操作 → 接口或本地能力 → 返回数据/错误”的对应关系，再逐项接入。将接口模型到展示模型的转换集中处理；时间与时区、空值、优先级及状态枚举按契约解释。

每个主要流程按实际需要覆盖首次加载、空数据、有数据、局部刷新、提交中、成功和失败。网络项目还需处理超时、断网，以及接口定义的认证失效、权限不足、冲突和部分成功等状态。

- 首次加载有占位或进度提示；刷新尽量保留已显示内容，不反复清空列表或重置滚动位置。
- 提交中阻止重复写入，保留输入；提交失败在相关位置说明原因并允许重试，不能先关闭表单再丢失草稿。
- 搜索、筛选和切页处理过期响应，避免旧结果覆盖新结果；返回列表保留合理的筛选与位置。
- 写入成功以后端确认结果为准；如果采用乐观更新，必须有失败回滚和重试策略。
- 数据读取失败不能当作“没有数据”；服务端删除、状态变化和权限变化使用明确提示及可用操作。

新增功能使用同一套视觉与动效规范。后端已经移除的能力调整入口与说明；尚未实现的能力明确标注依赖，不以固定示例数据伪装真实结果。演示数据必须与真实使用分离并标注。

### 八、资源占用与实现质量

尽量复用现有依赖、图片处理、列表、组件和构建缓存。需要保留原版时，使用独立分支或轻量工作副本，避免重复复制 SDK、依赖目录和大型构建产物。

优先使用当前技术栈的原生动效，不为基础过渡增加大型动画库、图片库或后台服务。大列表采用适当的惰性加载、分页或虚拟化，保持稳定 ID。不要在动画每帧重复请求接口、读取磁盘、排序日程或处理大图。

动画状态留在 UI 层，业务数据遵循项目既有的数据流和状态管理。异步工作按生命周期取消或正确移交；控制图片缓存，不保留无界历史页面。复用一个模拟器完成验证，避免同时启动多个实例，任务结束后清理本次不再需要的进程。

### 九、按项目实际技术栈使用 skill

如果环境可用，读取并使用 frontend-design 和 ui-ux-pro-max，针对当前产品、页面和技术栈检索规则。保持本文已经确认的 Repland 方向，不让通用模板覆盖用户偏好。

React/Next.js 项目再使用 vercel-react-best-practices；网页项目可使用 web-design-guidelines 和 webapp-testing。Compose 项目使用 Compose 指导及 Android/Compose 测试工具，不把网页 API、CSS 或 React 规则机械搬进原生界面。

skill 不存在时说明情况，继续使用适用的项目规范和已核实的设计要求；不要冒称已经安装、读取或执行。新增依赖与工具保持必要且精简。

### 十、实际运行验收与交付

实现后完成适合本次改动的构建和回归验证，并实际打开应用检查：

1. 主要页面及新增功能的入口、返回和真实数据流程。
2. 部分重叠、完全重叠、无重叠及未设置优先级时，总计与详细的对应关系；切换不写入计划。
3. 新增、编辑、保存、取消和失败重试，表单草稿与列表状态正确保留。
4. 头像选择成功、取消、失败、恢复默认，用户名校验和保存，重启后的资料状态。
5. 连续点击、快速切页、中途反向展开、系统关闭动画时，动作仍可靠且不会重复提交。
6. 窄屏、横屏、较大屏幕、200% 字体、深色模式与软键盘下的布局和可操作性。
7. 屏幕阅读器标签、焦点顺序、选中/展开状态及拖拽操作的可用替代入口。

对新的排序、时间投影、接口映射及关键状态处理增加有价值的测试；复用并维护现有测试。测试结果如实报告，不沿用旧版测试数量充当本版证据。

交付可运行版本、打开方式、主要变更、验证结果和仍受后端限制的事项。提供关键页面的修改前后截图，以及约 30–60 秒实际操作录屏，展示切页、点击、总计/详细切换、展开收起和资料编辑；尽量采用一致的操作步骤、窗口与测试数据，以便比较。无法运行的环节明确说明，不用静态拼接图代替运行录屏。

最终效果应当保留我认可的柔和多色与清晰层次，同时让新功能在真实数据、等待、成功、失败和连续操作中都表现完整。请按上述要求持续完成实现与验证。
