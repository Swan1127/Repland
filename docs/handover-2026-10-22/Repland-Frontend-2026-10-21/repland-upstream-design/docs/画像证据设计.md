## 0. 一句话结论

**mem0 的画像模型值得借鉴的是它的"状态"，不是它的"生成"。**
它用 LLM 把记忆概括成一段画像 —— 这条我们不抄（违反"结论可逐条回溯到来源"）。
但它坚持"**读画像时先看状态、不要看对象是否为空**"，这条我们该抄，因为我们的证据页现在正犯着它点名的那个错：
把「一条日志都没有」「有日志但没确认反馈」「材料齐了但还没生成」压成同一句"暂无画像证据"。

**studypath 的前端值得借鉴的是它的"分段"和"空态"，不是它的"进度条"。**
一根 40% 的进度条放在计划卡上是对的，放在画像证据上是错的 —— 那会让用户以为"我被画像了 40%"，
而"被画像多少"是一个**不存在的目标**。这正是我们要拒绝的量化推断。

**落地代价：0 次 schema 变更、0 次迁移、1 个新纯函数、1 次端口返回类型调整、UI 分段。**
原路线图要求的 `sourceLogIds` 列**不做**，理由见 §8。

## 2. 框架：三个被混为一谈的"用户画像"

"用户画像"这个词同时指三件不同的事。不先分层，讨论必然打滑。

| 层 | 名字 | 它回答的问题 | 数据形态 | 谁生成 | 可回溯？ |
|---|---|---|---|---|---|
| **L0** | **身份 Identity** | 你是谁 | 昵称、头像 | **用户自己填** | 不需要 |
| **L1** | **证据 Evidence** | 你**做过**什么 | 一条条可点开的执行日志 | **纯函数**（确定性） | **是**（这就是它的定义） |
| **L2** | **画像 Profile** | 你是**怎样的人** | 对 L1 的概括 | **？← 全部争议在这** | 取决于生成方式 |

三个参照物分别站在哪里：

| | L0 身份 | L1 证据 | L2 画像 | 生成方式 |
|---|---|---|---|---|
| **mem0** | `user_id` 只是分区键，不是画像 | 有（memories，原子事实） | **有** | **LLM** 按 JSON Schema 概括 |
| **studypath** | 有（头像 + 昵称，存本地文件） | **无** | **无** | —（"学习统计图表"还在它的 Roadmap 上没做） |
| **我们（repland）** | 有（`ProfileIdentity`，纯函数 + 薄 Android 层） | 有（`ProfileEvidence` + 逐条 `ProfileEvidenceSource`） | **半有**：结论是代码算的 | **纯函数** `ProfileEvidenceGenerator` |

**这张表就是全部结论的来源：**
- studypath 在 L1/L2 上是**空的** —— 所以"对比他的前端"只能对比**视觉与信息结构**，对比不到画像本身。
- mem0 在 L2 上**最成熟**，但它的成熟来自 LLM —— 恰好是我们唯一不能用的手段。
- 我们**唯一**缺的是 mem0 那条纪律：**把"为什么这里是空的"变成用户看得见的状态**。

## 3. mem0 的画像模型（事实，非推断）

来源：`mem0/docs/platform/features/user-profiles.mdx` + `mem0/client/main.py`（本次克隆，逐字读）。

**它的定义（原文）：** "Memories are individual facts. A profile is the summary of all of them for one entity:
a single structured object, shaped by a JSON Schema you define, that Mem0 keeps current as new memories arrive."
并且："Search answers *what did this user say about X*. A profile answers *who is this user*, **in one read, with no query to write**."

**它的机制：**

| 机制 | mem0 的做法 |
|---|---|
| 形状 | **JSON Schema**，由开发者声明；**每个字段必须带 `description`**（"description 就是指令"） |
| 生成 | **LLM** 把 memories 概括进 schema；`custom_instructions` 追加引导 |
| 时机 | **异步**。约每 10 条消息自动刷新一次，另有 `generate_profile` 手动触发 |
| 状态 | `succeeded` / `pending` / `insufficient_data` / `not_enabled` / `failed`；**"branch on `status`, not on the emptiness of the object"** |
| 更新 | **增量合并**（incremental），不是每次全量重建；`generation_count` 记代数 |
| schema 变更 | **只作用于下一次生成**；被移出 schema 的字段在下次生成时**被剪掉** |
| 调试 | `sample_profiles` 拿真实记忆跑几个用户，先看产出再定 schema（**要计费，不是空跑**） |
| 边界 | 配置按 project 隔离，画像**不跨 project** |

**逐条判定 —— 我们该不该抄：**

| mem0 的做法 | 判定 | 理由 |
|---|---|---|
| **状态机 + "先看状态"纪律** | ✅ **抄** | 这是本次最大收获。见 §6.1 |
| "一次读取拿到一个对象" | ⚠️ **改写后抄** | 我们要的是**顶部一句摘要**，且它必须是**已有结论的拼接**（纯函数 join），不是新生成的一段话 —— 否则立刻变成不可回溯的断言 |
| 字段必须带 description | ✅ **抄（换成编译期形式）** | 对应物：`ProfileEvidenceScope` 每个值必须在 KDoc 里写清"说什么、不说什么"。我们没有模型会去猜，但**人**会 —— 新 scope 会变成一个没人知道往里放什么的筐 |
| 先抽样再定 schema | ✅ **抄（换成测试形式）** | 对应物：用夹具 install 断言**渲染出来的结论文本**，这样加一种结论时是"先看到它长什么样"才合入 |
| **LLM 概括生成** | ❌ **不抄** | 违反本仓红线"结论可逐条回溯到来源"；且 `ProfileEvidenceGenerator` 的结论**明写**"不据此推断效率或能力"。LLM 概括在定义上就是推断 |
| **异步生成 / `pending`** | ❌ **不抄** | 我们没有服务端；生成是对日志的一次**微秒级纯函数重算**。把同步计算包装成状态机 = **发明一个不存在的异步**，测试只能测假状态 |
| **增量合并** | ❌ **不抄** | mem0 合并是因为 LLM 全量重建贵。我们全量重算免费，而且**确定性正是能做变异测试的前提**；合并会引入状态漂移 |
| `generation_count` | ❌ **不抄** | 我们每次读都重算，没有"第几代"。硬造一个计数器 = 给一个不存在的流程记账 |
| JSON Schema | ❌ **不抄** | schema 是**运行时**校验；我们的结论集合是**编译期**穷尽的 sealed/enum。用 schema 是**降级**，不是对齐 |

## 6. 设计

### 6.1 域层：`ProfileCoverage` —— 把"为什么是空的"做成纯函数（本次核心）

新增 `domain/model/ProfileCoverage.kt`：

```kotlin
/** 覆盖率状态：证据页现在能说出自己为什么是空的。四态互斥，判定按此顺序短路。 */
enum class ProfileCoverageStatus {
    /** 连一条执行日志都没有。 */
    NO_LOGS,
    /** 有日志，但没有一条带确认反馈 —— 生成器对空反馈不产出任何结论。 */
    NO_CONFIRMED_FEEDBACK,
    /** 有可生成的材料，但库里还没有行（没点过生成，或生成后被删光）。 */
    NOT_GENERATED,
    /** 库里已有结论行。 */
    READY,
}

data class ProfileCoverage(
    val status: ProfileCoverageStatus,
    /** 生成器实际会采用的有效日志里，带确认反馈的条数。 */
    val confirmedFeedbackCount: Int,
    /** 有效日志覆盖到的不同任务数。 */
    val coveredTaskCount: Int,
    /** 已落库的结论行数。 */
    val rowCount: Int,
) {
    companion object {
        val EMPTY = ProfileCoverage(NO_LOGS, 0, 0, 0)
    }
}

object ProfileCoverageRules {
    fun of(
        effectiveLogs: List<TaskExecutionLog>,
        tasks: List<Task>,
        rowCount: Int,
    ): ProfileCoverage { /* 纯函数，见下 */ }
}
```

**判定顺序（短路，且是规格不是实现细节）：**

```
rowCount > 0                                        → READY
effectiveLogs 为空                                  → NO_LOGS
带确认反馈的 effectiveLogs 为空                      → NO_CONFIRMED_FEEDBACK
否则                                                → NOT_GENERATED
```

**关键设计点：`effectiveLogs` 必须与生成器**同一份**。**
生成器现在的第一步是"剔除被修正的、剔除 `REPLACEMENT` 的" —— 这段逻辑目前是 `ProfileEvidenceGenerator` 内部的私有步骤。
如果覆盖率**自己**再写一遍"带反馈的日志"过滤，就会有两份同义谓词：

> 覆盖率说"数据充足"、生成器却一条都不产出 —— 用户点了按钮，什么都没发生，而页面还告诉他材料是齐的。

所以设计上把这一步**抽出来**：

```kotlin
// ProfileEvidence.kt 内，改为 internal，生成器与覆盖率共用
internal fun effectiveLogs(logs: List<TaskExecutionLog>): List<TaskExecutionLog>
```

**两者由构造保证一致，而不是靠两处代码碰巧写对。** 这是可测的一半，也是变异测试能钉住的一半。

### 6.2 数据层：快照承载（**零迁移**）

`RoomProfileEvidenceRepository.observe()` 的 `combine` **已经同时拿到了** evidence、logs、tasks。
唯一要动的是**返回类型**：让 `observe()` 一并返回覆盖率。

```kotlin
data class ProfileEvidenceSnapshot(
    val rows: List<ProfileEvidence>,
    val coverage: ProfileCoverage,
)

interface ProfileEvidenceRepository {
    fun observe(): Flow<ProfileEvidenceSnapshot>     // ← 由 Flow<List<ProfileEvidence>> 改
    // generate / updateConclusion / delete 不变
}
```

- **不动 Room**：不新增列、不新增 DAO 方法、不新增迁移。`version` 保持 21。
- **不动 `ProfileEvidenceSource`**：它仍然只认执行日志。
- **不动指纹**：`sourceFingerprint` 的构成不变，因此**老库不会因为本次改动多长出一行**。

### 6.3 UI：药丸 + 分段 + 分状态空态

**① 顶部状态药丸**（抄 studypath 的 99dp 胶囊形状）

```
[ 数据充足 ]   依据 12 条确认反馈 · 覆盖 4 个任务
[ 尚未生成 ]   材料已就绪，点下面的按钮生成
[ 缺少确认反馈 ]  有 7 条执行日志，但都还没有确认反馈
[ 还没有执行记录 ] 去任务里记录一次执行，这里就会有内容
```

**② 证据卡内三段式**（抄 `SectionLabel`：等宽小字 + 延伸细线）

```
结论
  已确认记录 12 条执行反馈；其中 5 次实际投入共 240 分钟；不据此推断效率或能力。
────── 已计入的来源（12） ──────────────────────────
  · 高等数学 完成 2026-10-08 09:31 · 3f2a1b0c
  · ...
────── 相关工具产出（未计入上面的结论） ─────────────
  · KWL 学到了 · 高等数学 · 极限的存在性取决于左右极限是否相等
  · 还有 3 条
```

**为什么必须是两段而不是一段：** 结论句里写的是"已确认记录 **N** 条执行反馈"，N 是**数出来的**。
工具产出不属于 N。放进同一列表 = 页面在暗示一个它没有的计数。分段把这件事从"一句话的声明"变成**结构**。

**③ 空态分四种文案**（抄 `EmptyHint` 的"emoji + 一句话 + 下一步"）
按 `ProfileCoverageStatus` 穷尽 `when` —— **加一个状态 = 编译错误**，不可能再漏一个分支。

### 6.4 导出

`LocalDataJsonExporter` 顶层已有 `toolOutputs` 数组（本次已加）。
本次设计**不再新增导出字段** —— 覆盖率是**读时派生**的，把它写进导出文件等于把派生量固化成事实，
下次导入时它会与重算结果不一致。导出文件里保留的是**可重算的原料**，不是派生结论。

---

## 7. 明确不做的（含理由）

| 不做 | 理由 |
|---|---|
| LLM 生成画像文本 | 违反"结论可逐条回溯到来源"；生成器明令不推断能力 |
| 异步状态机 / `pending` | 生成是同步纯函数重算，包装成异步 = 发明一个不存在的状态 |
| 增量合并 | 全量重算免费且确定；合并引入漂移，破坏可测性 |
| `generation_count` | 没有"第几代"的概念 |
| JSON Schema | 编译期穷尽 > 运行时校验 |
| **`sourceLogIds` 列 / 工具产出成为一等证据** | 见 §8 |
| 证据页进度条 | 画像没有目标，条会凭空造出一个指标 |
| 反射接入 | 反射按日期索引，挂不到任务上；挂上去就是**发明**一个关系 |

## 8. 对 §4 P2 #17 的判定：改写，不是缩水

路线图原文：

> 17 | 工具产出 → 画像证据的闭环：`ProfileEvidenceSource` 目前只认执行日志，需扩溯源模型（来源可为日志或工具产出），
> 涉及 `sourceLogIds` 列、证据页 UI、`LocalDataJsonExporter` 导出格式

**本次判定：不做"扩溯源模型"。** 理由不是省事，是那个形状**本身是错的**：

1. **计数会被污染。** `ProfileEvidenceSource` 是**被结论数出来**的东西（"已确认记录 N 条执行反馈"）。
   工具产出进去，N 就变成一个混合了两种东西的假数。§5 第 8 项 ⑧ 已论证过两条错路
   （塞空来源 → 产出"不透明结论"；伪造日志 → 三个消费者全部误读）。
2. **mem0 自己的模型就是"分开"的。** memories 是事实，profile 是**概括** —— profile **从不吸收** memories，
   事实始终留在原处。我们"工具产出作为**未计入**的补充说明"是**同一个形状**。
3. **`ProfileCoverage` 才是 mem0 那边真正缺的东西。** mem0 的 `insufficient_data` 之所以有价值，
   是因为它让用户知道"不是你没有被画像，是数据还不够"。我们把这条拿了过来，**代价为零 schema 变更**。

所以 §4 P2 #17 应改写为：

> 工具产出以**未计入**的补充说明附着到相关结论（`ProfileEvidenceOutputs.attach`，派生、不落库、不参与计数），
> 并新增 `ProfileCoverage` 让证据页说出"为什么这里是空的"。
> **不扩溯源模型、不加 `sourceLogIds` 列** —— 理由见 `docs/画像证据设计.md` §8。

## 9. 测试与变异验证计划

**新增测试**

| 测试 | 钉住什么 |
|---|---|
| `ProfileCoverageRulesTest` | 四态各一；**顺序**（有行时即便日志为空也是 READY）；边界（1 条反馈恰好跨过 `NO_CONFIRMED_FEEDBACK`）；`coveredTaskCount` 按**不同任务**去重而不是按日志数；空输入 |
| `ProfileEvidenceViewModelTest`（扩） | 快照改型后 UiState 仍正确；覆盖率随行数变化 |
| `ProfileEvidenceCardTest`（源码守卫） | 每个 `ProfileCoverageStatus` 都有一个**已声明的**文案键；每个键两语言都存在；**无 `else` 分支**（穷尽 `when`） |
| `I18nResourceTest` | 自动覆盖新键（两语言键集相等 + 占位符类型相等） |

**变异验证（沿用本仓纪律：预测集 = 方法名集合，字节级还原）**

候选变异体：
- 判定顺序反转（`rowCount > 0` 从第一句挪到第三句）→ 必须让"有行且无日志"那条红；
- 把 `NO_CONFIRMED_FEEDBACK` 与 `NOT_GENERATED` 对调 → 必须让这两态各一条红；
- `coveredTaskCount` 用 `logs.size` 冒充 → 必须让去重那条红；
- **让覆盖率自己重写一遍过滤**（而不是共用 `effectiveLogs`）→ 必须让"覆盖率与生成器一致"那条红。
  **这条是本设计里最重要的变异体** —— 它测的正是"两份同义谓词"这个缺陷类；
- 药丸文案键接到错误的 `ProfileCoverageStatus` → 必须让源码守卫红；
- 文档化缺口变异体：UI 里的 `when` 若被改成带 `else`，**JVM 测试抓不到**（无 Compose 测试）——
  做成 **G 类**（预期存活）并写明它是缺口，而不是假装覆盖了。

## 10. 落地顺序（每步独立可验证）

| # | 步骤 | 产物 | 验证 |
|---|---|---|---|
| 1 | 抽 `effectiveLogs`（行为不变） | `ProfileEvidence.kt` | 现有测试全绿（**这一步不改行为，只改可见性**） |

**第 1 步是刻意的顺序：先让两个消费者共用同一个谓词，再让覆盖率存在。**
反过来做（先写覆盖率、再回头对齐过滤）几乎必然写出两份过滤，而且**测不出来** ——
因为两份过滤在绝大多数输入上给出相同答案，只有边界上分叉。
