### QA-023 — 模型处理中可确认临时草案及重复发送

状态：源码确认；0.1.12 禁用处理中确认和发送入口，隔离 QA 测试验证延迟回复时两个按钮均不可操作，最终 50 项同源专项设备回归通过；当前版真实请求可见“处理中…”。P1。

首轮请求前生成本地候选，但模型未返回时确认入口仍可用，用户可能误确认尚未校对的临时建议。现等待期间禁用确认和重复发送，显示“处理中…”，编辑或来源变化仍丢弃晚到响应，不扩大模型写入权限。

## 缺陷清单

### QA-001 — 在硬约束时间段放入任务会使正式包崩溃

| 字段 | 内容 |
| --- | --- |
| 优先级 | P0 / 阻断核心排程 |
| 状态 | 已确认（当前安装包日志） |
| 影响 | 任务放入首页日轨道时，应用主进程终止；用户输入流程被打断。 |

复现步骤：

1. 在首页日轨道中已有课程、固定事项或休息等硬约束。
2. 从“待安排”选择一个新任务，指定与该硬约束重叠的时间后确认放入轨道。
3. 当前安装包崩溃。

期望：在确认前拦截冲突或显示可恢复的错误提示；应用不能终止。

实际：设备 crash buffer 记录了 `FATAL EXCEPTION: main`，进程为 `com.swan1127.repland`。首个异常为：

```text
java.lang.IllegalArgumentException:
A task cannot overlap a course, fixed commitment, or rest block.
  at RoomPlanRepository.requireNoHardTimeConstraintOverlap(...:254)
  at RoomPlanRepository.requireValidPlanSegments(...:220)
  at RoomPlanRepository.placeTask(...:135)
```

初步定位（非修复方案）：异常从数据层校验直接穿透了 `PlanViewModel` 的协程。日轨道 UI 只判断“同一轨道”是否重叠，并提示可换轨并行；旧正式包的数据层却把课程/固定事项/休息视为跨轨道也不能重叠，二者规则不一致。

### QA-002 — 崩溃包与当前工作区的版本标识无法区分

| 字段 | 内容 |
| --- | --- |
| 优先级 | P1 / 发布与排障 |
| 状态 | 已确认 |
| 影响 | 无法仅凭用户提供的版本号判断其是否仍在运行会崩溃的旧实现，难以指导升级、聚合崩溃或验证修复覆盖。 |

证据：当前设备上崩溃的正式包为 `0.1.0 (1000)`；当前工作区的 Gradle 默认版本仍为 `0.1.0 (1000)`，但工作区已经不含 crash trace 中的 `requireValidPlanSegments` / `requireNoHardTimeConstraintOverlap` 实现，隔离内测包会在同轨冲突的前置检查中禁用确认且不崩溃。这说明同一发布标识可能对应了不同的行为版本。

期望：每次可分发行为变化均使用新的、可识别的 `versionCode`，并保留可追溯的构建来源。

### QA-004 — 助手草案的任务 ID 在新增保存时被替换

状态：源码确认；候选实现已修改，批量 Repository 测试通过。

原实现创建任务草案 UUID 后，`RoomTaskRepository.save` 在新增时另生成 UUID；助手随后按草案 ID 放置时段，造成时段引用不对应保存的任务。现保留显式草案 ID，批量新增与放置在一个数据库事务内完成，并用重复确认/冲突回滚测试检查不会留下孤立引用或半份数据。

### QA-005 — 助手编辑草案切页/重启丢失，旧回复可覆盖新输入

状态：源码确认；0.1.2 候选已实现持久化及请求版本保护，最终验收见交付进度。

原助手事项仅保存在页面 `remember` 内存中，没有数据库恢复；远程请求返回后未检查用户是否已编辑输入。现保存输入、意图、事项引用和上下文摘要；日期/摘要变化后拒绝确认，晚到回复不覆盖新输入，失败事务保留草案，成功事务清理。远程错误采用受控测试回复验证，不等同于真实服务验收。

### QA-006 — 自定义轨道只在当前页面有效，标识依赖占用位置

状态：源码确认；0.1.2 候选已实现稳定 ID 与持久化，最终验收见交付进度。

原自定义轨道在页面内存中，创建时使用随当天占用轨道数量变化的索引标识，空日没有建轨道入口。现独立保存命名轨道，并在日/周/月与草案编辑中按 ID 显示名称；旧时段引用不改写，空日可建轨道，重名明确拒绝。

### QA-007 — 旧 internal 包获得焦点时发生 ANR

### QA-008 — 纯排序预览仍使用时间轴说明

### QA-009 — 更换模型服务地址时可继续沿用原密钥

状态：源码确认，0.1.4 候选已拦截，配置 Repository 专项测试通过。P1 安全/配置问题。

原实现 API Key 留空表示保留密钥，但服务地址可同时改变，后续请求会向新服务发送原密钥。现有已存密钥且地址变化时，必须重新输入该服务的密钥，否则不保存新配置；未发送真实凭据。请求完成后配置版本变化也会拒绝旧回复。该测试使用专用 QA 偏好文件和无效测试密钥，不访问外部服务。

### QA-010 — 自由输入修改已有任务时意图仍停留在新增

状态：0.1.5 开发专项设备测试复现，已修正，24 项专项设备测试复测全部通过。P1 助手流程问题。

未主动选择“安排今天”时，“把原任务1改到12点”被本地规则默认归入 CAPTURE_TASKS；AI 即使返回有效已有任务引用，确认按钮仍因新增模式保护而禁用。现未明确选择模式、且回复包含有效已有任务引用时，切换到调整流程；用户明确选择“新增事项”时不自动转换。测试使用假 Advisor，不访问真实 API，不改用户正式数据。

### QA-011 — 助手保存时段会覆盖独立任务排序

状态：专项设备回归样例复现，0.1.6 已修正，最终 11 项相关设备复测通过。P1 数据一致性问题。

已确认计划顺序为 A/B，任务页独立排序改为 B/A 后，助手调整 A 的时段；原保存逻辑把旧计划顺序 A/B 再写回独立顺序，测试失败为 `expected [b, a] but was [a, b]`。现保存助手安排时优先保留工作区独立顺序，再补齐计划中的剩余引用和新增事项，不因移动时段重排已有任务。测试仅使用内存 Room 与 QA 包。

### QA-012 — 底部确认后成功提示可能处于屏幕上方

状态：0.1.6 QA 手动流程发现，已补充可见位置与输入焦点处理，最终两项收据 UI 专项复测通过。P2 反馈可见性问题。

用户在长草案底部确认，草案清空后页面保留原滚动位置，而成功结果卡插入顶部；数据已经提交，提示却可能需要手动回到上方才能看见。现新增成功结果且当前输入/草案已清空时，清理输入焦点并直接回到页首；不会因为旧结果或仍在编辑的新输入反复抢走位置。新增 UI 样例从底部确认，并验证结果入口可见、输入已失焦。

### QA-013 — 专注计时退出或重启后丢失，单轮结束等同整个任务完成

状态：源码确认，0.1.7 已替换为持久化执行会话，仓库及界面专项回归通过；真机后台行为仍待验收。P1。

原计时使用页面 remember，每次进入触发开始，退出后重新计时；“本轮完成”直接完成任务，未区分一轮与整项。现保存任务/计划/时段引用与运行、暂停时间，单任务一次只保留一轮；返回和重启可恢复，重复结束拒绝，状态变化与证据一并事务保存。整项完成、部分完成、继续进行和跳过分别由用户明确选择。

### QA-014 — 未提供实际时长的完成操作会写入推测耗时

状态：源码确认，0.1.7 已移除推测，生命周期及零秒执行专项回归通过。P1 数据真实性问题。

原完成未填实际时长时，用距最近 IN_PROGRESS 日志的墙钟时间或任务总预计时长补值，包含休息或根本未实际计时的情况。现未知实际时长保持空值；仅明确反馈或用户开始的专注会话累计运行时间记录耗时，暂停不计。旧历史不改写。

### QA-015 — 开始专注后自动弹出的重排草案覆盖计时界面

状态：0.1.7 QA 手动复现，已改为用户主动查看，真实 Activity 专项复测通过（无跳过）。P1 工作流中断。

任务开始使 updatedAt 变化，旧 LaunchedEffect 自动生成草案并弹出预览，盖住新执行对话框。现仅在今日页显示可行动提示，由用户选择预览；执行面板打开时不显示规划模态。开始会话与 Activity 重建样例增加“没有草案被自动生成/弹出”断言。

### QA-016 — 历史恢复未使用当前约束及执行保护的统一确认入口

状态：8 项专项设备样例复现 7 项失败；0.1.8 开发修正后，与生命周期/专注仓库合计 22 项专项回归通过。额外边界样例继续回归。P1。

RoomPlanRepository.restore 原来直接复制旧版本并替换当前计划，未经过 accept 的课程/固定事项/休息/锁定及活动专注保护，也未将顺序/草案清理与版本替换放入同一外层事务。现恢复与普通确认共用内部提交入口，重新校验未来时段的当前约束；已结束任务的未来时段不复活，过去源历史与执行证据保留。注入顺序写入失败时，计划版本、顺序和草案完整回滚。测试只操作隔离 QA 内存数据库。

### QA-019 — 首轮已有任务识别与临时新建草案身份冲突
